# sim/ — Isaac Sim scene (`sim/scripts/setup_scene.py`)

Moved out of the root CLAUDE.md (loads when working under this directory; the root file links here).

**Sim (`sim/scripts/setup_scene.py`, run via `--exec` in the Isaac streaming app; `./sim` is mounted at `/sim`):**
1. URDF → USD import, cached per model in `sim/generated/<model>/` and invalidated by a stamp file (`.import_stamp`: import settings + URDF mtime/size) or `FORCE_REIMPORT=1`. The importer output path is fragile — the script deletes each model's `usd_dir` first so it doesn't write `<model>_1/`, `<model>_2/`, ….
2. **Scene, then robots on request.** `main()` imports (or checks the cache of) *every* model with assets whose params could be derived (`load_model_params`, see 4.) first -- the importer opens its output in the USD context (`stage_utils.open_stage`), so it can't run once the scene is open; a model whose URDF changed after the sim started is refused at spawn ("restart the sim") -- then builds the world (lavender rows placed for `SCENE_LANES` lanes, default 3, not for a robot count), leaves the timeline **stopped** (nothing simulates until robots are spawned; `spawn_fleet` plays it after the last robot of a request), writes `sim/generated/fleet/state.json` (`scene: ready`, `models`, `default_poses` for 0-8 robots, `lavender_rows`) and runs `spawn_loop`. That polls `spawn_request.json` (written by `scripts/fleet_ctl.py`; `{id, robots: [{model, x, y, yaw_deg}]}`, slot = list index, namespace `robot_namespace(slot, model)`); a new id is validated (`parse_request`: known model, |x|,|y| <= 38 m, >= 1 m apart, no duplicate namespace -- a rejection leaves the robots alone) and `spawn_fleet` stops the timeline (masses/new articulations need a fresh start), deletes the old robots (`DeletePrims` on `/World/<ns>` + `/Graphs/<ns>`), spawns the new ones (`spawn_robot` = translate + rotateZ), re-aims the viewport and plays. **Replacing robots restarts the sim** (`fleet_ctl.spawn`, when `state.json` lists robots): the request is written with `at_start: true`, which the running `spawn_loop` ignores, then `docker restart`; at start `spawn_loop` spawns a pending request the previous run never answered (`state.json`'s last `spawn.id`, read before it is overwritten) and falls back to `applied_request.json` if it is rejected (`last_error` keeps the reason), then reports `boot: done`, which `wait_scene` waits for. Reason: removing robots in place (`spawn_fleet`'s `DeletePrims`, still used if a request arrives with robots present) made the RTX renderer abort (SIGABRT in `libnrend.so`, from a USD change ~15 s later) on a headed 3-robot respawn, and logged `ScriptNode.release` errors; the restart costs ~27 s (24 s scene + spawn) and was verified headed: two respawns, a rejected respawn (reason reported, previous robots back) and a reset, all alive. Spawning into an empty scene stays in place (verified headed, 2 min). **Reset without a restart:** `FLEET_CONTROL` (`control.json`, `{id, action: "reset"}`, written by `fleet_ctl.reset` / the UI's *Reset scene*) makes `spawn_loop` call `reset_timeline`: stop, 5 frames, play, answered as `state.json` `reset: {id, state: done}`, ~3.5 s; `fleet_ctl.reset` stops the robot containers before writing it and starts them after, so no robot-side process (a `cut_stem` run, MoveIt, the EKF) acts on the restarted scene. Verified with the 3-robot fleet (looks `full`, headed, 4 resets): robot back within 2 mm (GPS), the sim's 23 ROS nodes not duplicated, drives normally afterwards. An id left over from a previous run is not replayed. **Deleting a graph does not run its ScriptNodes' `cleanup()`** (seen live: the removed robot's `cmd_vel_sub_*` node stayed in the ROS graph), so the scripts that create rclpy nodes (CMD_VEL/GPS/LIDAR2D/LIDAR3D) register them in `sim/scripts/fleet_nodes.py` and `spawn_fleet` destroys them there. A successful request is copied to `applied_request.json`; at start the sim spawns that one (else a pending request), and ids it already answered are not replayed, so a sim restart restores the last working robots even after a rejected request. Robot looks are applied per model at spawn (`apply_robot_looks(models)`, once per model). `default_poses(n)`: `SCENE_LANES` robots 1.6 m apart at x=0, further ranks 2.5 m behind -- identical to the old layout up to 3 robots. `platform/odom` and the `ground_truth` TF start at zero at the spawn pose (`IsaacComputeOdometry`), so they don't show the yaw; GPS does (verified: yaw 90 deg, drive forward -> latitude +1.0 m, longitude unchanged). Per robot it adds a D435i USD camera, and builds one OmniGraph per robot using `isaacsim.ros2.bridge` nodes: `cmd_vel` (`geometry_msgs/TwistStamped`, like the real Clearpath Jazzy platform: `ROS2SubscribeTwist` only takes plain `Twist`, so `CMD_VEL_SCRIPT`, a `ScriptNode` with an in-process rclpy subscriber like the GPS one, stands in for it with the same outputs; `teleop`, `drive_test.py`, `calibrate_velocity.py` publish stamped) → differential drive → wheel velocity drives; publishes `platform/odom`, `platform/joint_states`, TF, and camera color/depth + camera_info. Topics are relative and land under each robot's namespace. Each distinct model's URDF→USD import (`import_urdf_if_needed`, per-model paths in `MODEL_ASSETS`) runs once regardless of how many robots use it.
3. **Simulation time (`USE_SIM_TIME`, default true):** `/Graphs/fleet_clock` (`build_clock_graph`, built with the scene, survives respawns) publishes `/clock` every played frame from `IsaacReadSimulationTime`, and each robot graph's `Stamp` node (the same node type; `IsaacReadSystemTime` when false) stamps odom, TF, joint states, IMU and, through a `stamp` input, the GPS/lidar script nodes; the camera helpers get `useSystemTime=False` and `resetSimulationTimeOnStop=False` (their own sim time restarts at 0 on Stop/Play by default: after one Reset scene the images were stamped 43 s against a `/clock` of 516 s; now every stream is within a frame of `/clock` before and after a reset, the camera one frame behind with async rendering). Measured: `IsaacReadSimulationTime` counts *physics* time -- odom stamps step 0.0333 s per frame at `SIM_RATE_HZ=22`/`PHYSICS_HZ=60`, not the timeline's 1/22 s -- so the frame-vs-physics caveat below does not affect `/clock`. `resetOnStop=False` on both: the default resets to 0 on Stop (spawn, Reset scene) and every ROS node would see time jump back; verified monotonic across `fleet_ctl.py reset`. 3 robots: `/clock` at 15.7 Hz, sim advances 0.52 s per wall second; `drive_test.py` 0.5 m/s -> 0.504 m/s in sim time, `calibrate_velocity.py` PASS, Nav2 goals (a300_00036/a200_0284 on the lidar, j100_0921 on the depth-image scan after a reset) and `cut_stem` (4/4) succeed with all three robots active.
   Time: the stage runs at `SIM_RATE_HZ` (compose fallback 20; this repo's tracked `.env` currently has 22, tuned for its 2-robot/FastDDS/async-rendering setup — treat it as a value to retune, not a constant). Set it to about the `render_fps` that `FLEET_DEBUG=1` reports, since rtf = fps / SIM_RATE_HZ (~15 for 3 robots on zenoh, ~10 for 5). PhysX substeps at `PHYSICS_HZ` (60) inside each frame, because camera rendering per robot is too costly for 60 Hz frames. Keep real-time factor ≈ 1.0 (check with `FLEET_DEBUG=1`). **Caveat measured during the velocity calibration:** Kit runs `floor(PHYSICS_HZ / SIM_RATE_HZ)` whole PhysX steps per frame, so at 22 Hz frames and 60 Hz physics a frame advances physics by 2/60 = 1/30 s, not the 1/22 s the timeline counts; `FLEET_DEBUG`'s rtf is timeline-based and overstates the physical real-time factor, which is `render_fps x (steps/PHYSICS_HZ)` (e.g. 14 fps -> 0.47, a robot commanded 1.0 m/s covers 0.47 m per wall-clock second and the odom stamps are wall-clock). `SIM_RATE_HZ` values where `PHYSICS_HZ / SIM_RATE_HZ` is a whole number (20, 15, 12, 10, 30) avoid the mismatch. The frame rate is also the WebRTC stream's frame rate. Measured levers (see README *Faster streaming*): `/app/asyncRendering=true` (+~20%, set via `FLEET_SETTINGS` in `.env`), fewer robots, `CAMERA_STREAMS=none`; resolution, streams, render mode, UI hiding and viewport size (`FLEET_VIEWPORT_RES`) don't change the fps because each camera render product has a fixed ~15–20 ms cost. `FLEET_MERGE_FIXED=1` does not work: it merges away `camera_0_link` and the scene build fails. **Cameras on demand (`CAMERA_ON_DEMAND`, default 1, `camera_on_demand_loop`):** a robot camera's hydra texture updates (`HydraTexture.set_updates_enabled`, the switch `OgnIsaacAttachHydraTexture` uses; `IsaacCreateRenderProduct.inputs:enabled` only stops downstream nodes, the camera keeps rendering) are on only while one of its topics has a subscriber (`count_subscribers` from an rclpy node in the sim, every 0.5 s, off 2 s after the last one leaves). Each camera renders for `CAM_WARMUP_S` (5 s) after every play/spawn/reset first: a camera that never rendered has no ROS publisher, so its topic is unknown and `ros2 topic hz`/`echo`/Foxglove (which take the type from the publisher) never subscribe -- seen live. Textures are found in replicator's `ViewportManager()._hydra_textures` (all contexts; `vp_manager.attach_hydra_texture` looks in a different context name than `get`). j100_0921 alone: 19.4 fps all on, 28.4 idle, 23.7 with camera_0 subscribed, 21.0 with both; reset verified. Toggling often is worse than not at all (alternating the 2 cameras every frame: 9.5 fps and no images; blocks of 5 frames: 18.6 fps, ~5 Hz each), so no round-robin / per-frame rate limiting.
4. **Model parameters are derived, not listed** (`load_model_params`/`derive_model_params`, at sim start, logged as `[fleet] params <m>: ...`): drive constants from `platforms[<platform>]` in `sim/config/model_params.yaml` (the real `clearpath_control/config/<platform>/control/diff_4wd.yaml` values, platform from `robot.yaml`'s `serial_number`), replaced by the robot.yaml's own `platform.extras.ros_parameters.platform_velocity_controller` calibration (wheel_radius x mean of the left/right multipliers, separation multiplier, max speeds); sensors from `robot.yaml` + the flattened URDF (Clearpath numbers a platform's built-in sensors first, e.g. j100's `imu_0`, so the yaml's k sensors of a kind are the k highest-numbered `<kind>_N_link`/`_laser` frames; the IMU's body is the link `flatten_urdf.py` merged its frame into, from `sim/assets/<m>/merged_links.json`, then up to the first link with collision/inertial); `has_arm` from `arm_0_*` joints, `wrist_camera` from `camera_1_link`, a ZED's `camera_0_left_camera_frame_optical`; then `robots[<m>]` overrides from the same file (only hand tuning or what an asset can't tell: `j100_0922`'s mass fix, and `j100_0936`'s calibration and IMU, since its stripped template and pre-`merged_links.json` asset can't be regenerated). Verified: for all 11 models the derivation reproduces the old hand-written `MODEL_PARAMS` exactly. **`chassis_link`** (what the drive/odometry OmniGraph targets, `DriveFront`/`DriveRear`/`Odom.inputs:chassisPrim`) is `chassis_prim()`: the one prim under the spawned robot with `UsdPhysics.ArticulationRootAPI`, read at spawn (a `chassis_link` override is still honoured). It used to be hand-picked and was the classic failure: it is not whatever looks like the chassis (a300/r100: `chassis_link`; a200/j100: `base_link`, j100's flipped when its fenders were merged into `base_link`), and a wrong one fails only at runtime with "Articulation controller failed". A robot with more than one root (an empty URDF root with several collision children, see `weld_empty_root_children`) is refused at spawn with that reason. **Running all 4 distinct models in one sim (4 robots, no repeats) reproduced a `PhysX Internal CUDA error` crash** on the dev machine; every single model alone and every combination of ≤3 distinct models tested fine — not root-caused, flagged in the README as a known issue rather than chased further.

Ridgeback (r100) is Clearpath's holonomic mecanum platform and drives omnidirectionally: forward/back and rotation use the same `diff_4wd.yaml` OmniGraph as the other models (`Diff`/`DriveFront`/`DriveRear`, built for every model regardless of `drive`), and a `BodyDrive` script node (`omni.graph.scriptnode.ScriptNode`, added only when the model's `drive` is `omni`) separately patches in real sideways (linear.y) motion every tick by reading the chassis articulation's *current* velocity (`isaacsim.core.experimental.prims.Articulation.get_velocities`/`set_velocities`, which act on a floating-base articulation's root — the same root `chassis_link` already has to be for the drive/odometry OmniGraph), decomposing it into the chassis' own body frame, replacing just the lateral component with the commanded `vy`, and writing the recomposed world-frame velocity back, leaving angular velocity untouched entirely. This two-part design exists because a straight port of Clearpath's real mecanum kinematics doesn't work in this sim: `isaacsim.robot.wheeled_robots.HolonomicController` (the obvious tool, and Isaac's genuinely-correct QP-based mecanum solver — `mecanumAngles` derived and verified against `omni_4wd.yaml`'s own `sum_of_robot_center_projection_on_X_Y_axis`) computes the right per-wheel speeds, but Ridgeback's own URDF gives every wheel a **plain cylinder `<collision>`** (the angled-roller detail is mesh-only, in `<visual>`), and this PhysX version has no anisotropic/directional friction (`frictionType` is fixed to `"patch"`, checked directly in the PhysX schema) to fake a roller's passive sideways slip — a spinning cylinder cannot produce sideways thrust no matter what any kinematic layer computes, confirmed live (wheels visibly spun correctly, robot barely crept while commanded to strafe). Driving those wheel joints with the (correctly computed) mecanum speeds anyway, purely for cosmetic spin, made rotation actively *wrong* — real, substantial reaction torque through the wheel joints fought the chassis's actual motion — so the wheel joints are left undriven for Ridgeback's lateral component and it doesn't visually spin its wheels while strafing. **Known limitation, found the same way both times it was tried (a full velocity override and, later, real diff-drive wheels for rotation):** a small *pure* in-place rotation command from a standstill (0.5 rad/s alone, verified live) is almost entirely absorbed — PhysX's contact solver resists breaking static friction to scrub a stationary wheel sideways far more than it resists continuing an already-sliding motion — while a larger command (2.0 rad/s) or one combined with any translation comes through close to correctly. Real wheel rolling for rotation was kept anyway (it's at least as effective as a direct override, and keeps rotation on the same already-proven code path as the other 3 models).

**Soft lavender (`soften_lavender`, `LAVENDER_SOFT`, default 1).** Real stems are thin and flexible: a robot brushing a plant pushes through it, while the woody crown at the centre stops it. Before this, every lavender collider (an exact triangle mesh, needed so the lidars, which are scene-query raycasts, see the plants) blocked the robots completely. `build_world` calls `soften_lavender` for every scene source. It works on whatever is under `/World/lavender`, so the built-in scene and `lavender_farm.usd` are handled the same way and the file isn't rebuilt. It puts `/World/lavender` in the `soft_plants` collision group, which filters against a `robots` group, and `spawn_robot` adds each `/World/<ns>`. Groups only filter contacts, so the raycasts still hit the foliage. It also adds a guide-purpose cylinder (not rendered, still a collider; `LAVENDER_CORE_RADIUS` 0.1 m, `_HEIGHT` 0.3 m) at each plant instance's bbox centre under `/World/lavender_cores/...`, outside the groups. **An inverted group (`invertFilteredGroups=True`, empty `filteredGroups`, i.e. "collide with nothing") is ignored in Isaac 6.0**: it was tried first and the plants still blocked, so the explicit pair is needed. Measured headless (a throwaway `docker run` of the Isaac image with `python.sh`, gravity-free 0.4 m boxes at 1 m/s, the boxes standing in for robots in the `robots` group):
- an instanced wrapper plant in the pair let the boxes through at full speed, against a stall at the foliage without the groups;
- on `lavender_farm.usd`, 381 cores sat exactly on the plants' bbox centres;
- a grid of 126 rays across a field plant hit it 38 times without softening and 44 times with it, at the same distances (the 6 extra are cores);
- a box aimed at a plant's centre stops at its core.

Farm plants are 0.45 m apart, so the cores (0.25 m gaps) still make a row a barrier you can't cross. Confirmed live by the user on 2026-10-03 (`lavender_farm.usd`, a300_00036): the robot drives through the foliage and the lidars still see the plants.

**Velocity calibration (every model, `scripts/calibrate_velocity.py`).** Requested: make the simulated linear and angular velocities match the commanded ones within 10% over 0-1 m/s and 0-1 rad/s, at low acceleration. Result with the settings below: every model within ~5% (worst single level ~8-9%) at 0.25 m/s², 0.5 rad/s², measured from the pose, see `last_session.md`. What it took, in order of how much each mattered: (1) **closed loop**: the wheel parameters alone (radius/separation) cannot do it, a skid-steer robot's in-place rotation had a dead zone (0.2 rad/s did not move, 0.5 gave 0.2-0.6x) and j100_0921's reverse was 0.6-0.9x; `VEL_CTL_SCRIPT` (a `ScriptNode` between cmd_vel and the `DifferentialController`, `VELCTL_DEFAULT` gains, per-model override `vel_ctl` in `sim/config/model_params.yaml`, `VELCTL=0` disables it) adds feed-forward + PI on the chassis' achieved forward speed/yaw rate. Everything that did NOT help the dead zone: wheel friction (0.1-0.4 with min-combine), wheel drive damping (x10, x1000), wheel speed, 360 Hz physics is costly (rtf halves) and only partly helps. (2) **measure from the pose, not PhysX's reported velocity**: the reported angular velocity read 0.02-0.03 rad/s too high (a 0.1 rad/s command "measured" 0.1 while the robot turned 0.078), so a loop closed on it settled 20% low; the published `platform/odom` twist now also comes from the pose (`VelCtl.outputs:odom_lin/odom_ang`), it was up to 25% off at low rates and wrong on the Ridgeback. The time base is `PHYSICS_FRAME_DT` (1/30 s at the default rates, see the Time paragraph). (3) **PGS solver + CCD on the wheels** (`build_world`, `enable_wheel_ccd`; NVIDIA forum: TGS barely turns skid-steer robots; same 60 Hz, no fps cost). (4) **Ridgeback**: `BodyDrive` now also sets the yaw rate and its sideways speed is fed back too (lateral 0.03x-0.83x -> 1.00x, yaw 0.74-1.0x -> 1.00x). (5) **`Diff` max speeds are `VELCTL_HEADROOM` x the robot's limit** (the command itself is clamped to the real limit inside `VelCtl`), otherwise the feedback saturated at the command. (6) the `j100_0922` mass fix above. Not changed on purpose: `wheel_radius` etc. keep the real calibrated values (a200_0284 / Jackals still go ~5-7% fast open-loop; the loop removes that). Stow the arm before measuring (`calibrate_velocity.py` does, from the SRDF `stow` state) to keep the centre of mass low. Run-to-run scatter at 0.1 rad/s is a few percent because the wheels stick-slip.

**Resting stillness (wheel brake + solver iterations).** With no `cmd_vel` at all (Diff's wheel targets exactly 0) the robots rocked forward/back: a300_00036 -17.6..+4.4 mm, 69 reversals and 0.4 deg of yaw in 60 s. Two causes: the wheel drives are pure velocity dampers (stiffness 0), which never hold a position, so the solver's small alternating contact torques integrated into wheel rotation; and with PhysX's default 1 articulation velocity iteration the resting contacts jittered (IMU z std 0.44 m/s^2, gripper fingertips 0.2 rad/s RMS). Fixes in `setup_scene.py`: `WHEEL_BRAKE_SCRIPT` (a `WheelBrake` ScriptNode per robot) latches the wheels' current angles as position targets with `WHEEL_BRAKE_STIFFNESS` 1e4 N*m/rad once the command is zero and the wheels are slower than 0.05 rad/s (or after 1 s), and sets the stiffness back to 0 on any non-zero command, so driving and the velocity calibration are unchanged; and `ARTIC_VEL_ITERS` (default 8) on every articulation root. Result on a300_00036: within -2.1..+0.8 mm and 0.06 deg of yaw over 60 s, same frame rate (64 position iterations added nothing and cost ~15% fps).

**Robot materials (`ROBOT_LOOKS`, `sim/scripts/robot_looks.py`):** the importer's materials are flat `UsdPreviewSurface`s (one colour, roughness 0.5), which made the robots look like smooth, spotless plastic. `apply_robot_looks(models)` (at spawn time, once per model; it only opens the model's own layers, never the scene's stage) rebinds every visual to an OmniPBR / OmniPBR_ClearCoat "look" from `/sim/generated/looks/looks_<mode>.usda`, chosen by `RULES`/`MODEL_RULES` (instance/mesh name, material name, colour class -- hue is judged in sRGB: the A300 yellow is linear (1, 0.47, 0)), modelled on `robot_data/pictures/`. Textures (albedo with dust/scratches, roughness, normal) are procedural numpy fields, generated once (~25 s) and cached by a stamp; parts have no UVs, so OmniPBR's object-space cubic projection is used, with `texture_scale` set per part from its mesh unit (mm-scaled STLs) so a tile is `TILE_M` everywhere. **How it edits instanced robots:** visual meshes are instance prototypes, so bindings can't be authored on the stage (instance proxies, cf. the 3D lidar crash); the bindings live in each model's `payloads/instances.usda` (meshes) and `payloads/base.usda` (URDF primitives such as boxes, not instanced) and are retargeted *in memory* (`Sdf.Layer.FindOrOpen`, never saved; `_held_layers` keeps the layers alive so the registry doesn't reload them from disk). Only `material:binding` (all-purpose) changes: physics bindings, colliders, masses are untouched. A tinted look needs one prim per colour (an instance can have several colours: the SICK's blue stripe once tinted its whole body). Modes: `full` (default), `basic` (constants, no textures), `0`. Errors only log and keep the importer's materials. Measured: no fps difference with 3 robots (off 8.8-9.3, full 9.2-9.7, basic 9.6-9.8 render fps). `FLEET_SNAPSHOT=<dir>` saves viewport PNGs of each robot (`snapshot_loop`) for comparisons.

**2D lidar, unblocked (history: superseded by "Lidars now cast their own rays" below):** `isaacsim.sensors.experimental.physics.Raycast`/`RaycastSensor` is a real, working, per-physics-step PhysX raycast sensor — the same module `IMU`/`IMUSensor` already use successfully, with its own independent `IRaycastSensor` C++ interface, entirely unrelated to the broken `isaacsim.sensors.rtx` pipeline. `LIDAR2D_READ_SCRIPT` authors one as a plain child of the real `lidar2d_link` prim (inheriting its mount pose automatically, same pattern `add_camera` uses) with a ray fan matching the real sensor's declared FOV (`LIDAR2D_ANGLE_MIN/MAX` ±2.356 rad, `LIDAR2D_NUM_RAYS` 541 — ~0.5° resolution, an approximation, not either real sensor's exact spec), and publishes `sensor_msgs/LaserScan` via a plain rclpy publisher (same reasoning as `GPS_READ_SCRIPT`: a per-tick computed reading, not a literal `SET_VALUES` case). **Real bug found in this "experimental"-namespace API itself**, isolated through a sequence of targeted single/few-ray tests rather than assumed: `get_data()['depths']` does not report a genuine per-ray distance — a 3-ray down/forward/up probe returned `depths=[0.1, 0.1, 0.1]` (exactly `min_range`) for all three regardless of what each ray actually hit, while the *same reading's* `hit_positions` were correct per ray (`[0,0,-0.1]`, a real close hit; `[3.77,0,0]`, a real hit on scene geometry; `[0,0,0]`, a genuine miss). Worked around by computing each ray's range as the Euclidean norm of its own `hit_positions` entry instead of trusting `depths` at all (`output_frame="SENSOR"`, the default, keeps `hit_positions` in the same local frame as `ray_origins`, so the norm is directly the range in metres); a `[0,0,0]` entry means no hit, remapped to `+Inf` per REP-117. Verified live on `a200_0333`'s Hokuyo: genuine, varied finite ranges (209/541 rays hit something, 1.36–9.99m, matching the scene's own known target-box/wall geometry), not a uniform placeholder.

**3D lidar:** the same `Raycast`/`RaycastSensor` mechanism, extended to `a200_0333`'s real Velodyne VLP16 (16 channels, real ±15° vertical FOV, 360 horizontal steps — 5760 rays total, publishing `sensor_msgs/PointCloud2` on `sensors/lidar3d_0/points` instead of `LaserScan`), reusing the same `hit_positions`-based range fix 2D lidar needed (the `depths` bug applies here too). **The very first attempt segfaulted the whole `a300-isaac-sim` container** (`Exited (139)`) — a real crash, not silently ignored: immediately disabled the new code and confirmed the rest of the fleet still came up cleanly before investigating further. Root cause, found by actually reading the log line just before the crash rather than assuming it was the 5760-ray count: `UsdStage::_ValidateEditPrimAtPath ... authoring to an instance proxy is not allowed` — `a200_0333`'s `sensor_arch` mount subtree (the VLP16's own real ancestor chain, unlike 2D lidar's non-instanced bracket mount) is USD-instanceable, so authoring the sensor prim as its child is rejected outright; the retry-on-exception pattern (safe for a genuinely transient "not ready yet" condition, which is all IMU/2D lidar ever hit) instead kept re-attempting the same permanently-failing call every tick against an instance proxy, which is what actually crashed the process. Fixed by parenting the raycast sensor under `chassis` instead (never instanced) and computing `lidar3d_link`'s real pose *relative to chassis* once, live, via `UsdGeom.Xformable(...).ComputeLocalToWorldTransform()` on both prims (a static offset, since both are real rigid links) — passed to `Raycast.create()` as explicit `translations`/`orientations` rather than relying on parent-child nesting. Retested the exact same 5760-ray configuration after the fix and it's completely safe — confirmed ray count was never the actual problem by testing incrementally back up to it (576→1152→3200→4800→5760, each a clean boot with real point data) rather than just assuming a smaller value was the necessary fix. `FLEET_DEBUG=1`: `render_fps` 12.1→10.4 with 3D lidar added on top of 2D lidar (~14% cost, not isolated from the scene's already camera-bound baseline).

**Lidars now cast their own rays (supersedes the plugin mechanism in the two paragraphs above).** User report: "headed mode, three robots spawning, the simulation crashes" (j100_0921 + a200_0284 + a200_0333). The sim segfaulted (exit 139) a second or two after play, inside `libisaacsim.sensors.experimental.physics.plugin.so`'s own per-physics-step update (minidump read with a small stdlib parser: faulting frame in that plugin under `omni.physx`'s step, a garbage pointer), i.e. the `Raycast`/`RaycastSensor` lidars. Isolated with a200_0333 alone (its *only* sensors are the two lidars -- it has no `imu_link`) as the first spawn at (0.4, -0.5): 6/6 crashes with the scene/spawn split, **2/4 with the pre-split one-shot startup** (so not a regression; the old fixed x=0 layout just rarely hit it), 0/5 with both lidars left out; either lidar alone still crashed. Ruled out: headed mode, vegetation colliders, the wheel brake, robot looks, when the sensor prims are authored (pre-authoring them at spawn didn't help), playing the scene before the first spawn, delaying the first reading by 3 s. Fix: `LIDAR2D_READ_SCRIPT`/`LIDAR3D_READ_SCRIPT` cast rays with PhysX's scene-query API (`omni.physx.get_physx_scene_query_interface().raycast_closest`) from the script node, per frame, from the lidar link's pose (2D) or chassis × the lidar's pose relative to it (3D, the instanceable `sensor_arch` again); no sensor prims, same topics/frames/messages, rays start at `range_min`, misses +Inf (2D) / dropped (3D). Directions are transformed with numpy, only the raycast call is per ray. The 3D scan is spread over `LIDAR3D_TICKS_PER_SCAN` (4) frames: a cloud every 4 frames (~5 Hz at 22 Hz), each channel cast from its frame's pose. Result: 0/5 crashes at the crashing configuration, the user's fleet 0/5 (both pose sets); data checked (2D 541 rays, ~150 hits 2.5-9.9 m on the lavender rows/trees; 3D ~3100 points, none within 1 m, z -0.66..6.9 = ground..trees). Cost, a200_0333 alone: ~29 fps without lidars, ~21 with both (~13 ms/frame for 541 + 1440 rays), about what the plugin's 3D lidar alone cost. The IMU still uses the same plugin (`IMUSensor`); it was never seen crashing (j100_0921 ran 6+ minutes), but it is the same code. Debug aids worth keeping: `docker logs` is lost when compose recreates the sim, so save it right after a crash; minidumps are in the `isaac-ov-data` volume (`Kit/Isaac-Sim Full/6.0/*.dmp.zip`), only the latest kept.
