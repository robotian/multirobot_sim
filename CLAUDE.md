# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**At the start of a session read `last_session.md`** — it records what has been built, decisions and their reasons, how things were verified, and open items.

## What this is

A simulated fleet of Clearpath robots (each with a RealSense D435i), one of A300/A200/Jackal(j100)/Ridgeback(r100) per slot (`ROBOT_MODEL_<i>` in `.env`, default a300), in Isaac Sim 6.0, driven over ROS 2 Jazzy. Isaac Sim runs in one container (WebRTC streaming, no local GUI); each robot is its own ROS 2 container standing in for the robot's onboard computer. There is no build system, test suite or linter — everything is Docker Compose plus a few scripts. It is a git repo (`main`, remote `origin` = github.com/robotian/multirobot_sim); `sim/assets/` and `sim/generated/` are gitignored because `scripts/gen_urdf.sh` and the sim's first start rebuild them, and `.env` is tracked (no secrets, but it holds this machine's LAN IP in `ISAACSIM_HOST`).

## Commands

```bash
scripts/x11_auth.sh                       # once per login: builds /tmp/.docker.xauth (needed for rqt_image_view in robot containers)
docker compose build                      # clearpath-robot:jazzy (robots + zenoh router) and a300-isaac-sim:6.0.0 (Isaac + system ROS 2)
scripts/gen_urdf.sh                       # regenerate sim/assets/<model>/{<model>.urdf,meshes,robot.yaml} for all 4 models from robot/config/robot.<model>.yaml.tmpl
scripts/fleet.sh [N|down]                 # choose the number of robots (0-8; writes NUM_ROBOTS to .env), restarts the sim, removes surplus robot containers, warns about ROBOT_MODEL_<i> set for an inactive slot (i >= N)
scripts/stop_sim.sh                       # stop and remove every container (docker compose down misses profiles outside NUM_ROBOTS; same as `fleet.sh down`)
scripts/colcon_build.sh [colcon args...]  # colcon build ~/colcon_ws (as `robot`) in every running robot container
docker compose up -d                      # sim + NUM_ROBOTS robots (default 3); watch with `docker compose logs -f isaac-sim` (lines prefixed [fleet])
docker exec -it a300_0000 bash            # shell in a robot (sources /etc/clearpath/setup.bash via /etc/bash.bashrc; ROBOT_NAMESPACE=a300_0000)
docker exec -it -u robot a300_0000 bash   # shell as the `robot` user, for ~/colcon_ws (shared across all robot containers)
docker exec -it a300_0000 teleop          # keyboard control (i/j/l/,/k), publishes /a300_0000/cmd_vel
docker exec -it a300_0001 rviz            # RViz with fixed frame odom, RobotModel, TF, camera (robot/config/robot.rviz.tmpl, model-agnostic)
docker exec a300_0000 camera_view [depth] # rqt_image_view of the D435i on the host display (needs x11_auth.sh)
docker exec a300_0000 bash -c 'python3 /scripts/drive_test.py [lin_x] [ang_z] [seconds]'   # smoke test: commanded vs. odometry
```

- `gen_urdf.sh` runs inside the robot image, so build it first. It always (re)generates all 4 models unconditionally, so it doesn't need to know which are in use. Re-run it after changing any `robot.<model>.yaml.tmpl` or `flatten_urdf.py`.
- Plain `docker exec <c> python3 ...` has no ROS environment (the entrypoint only covers PID 1); wrap in `bash -c` (the image sets `BASH_ENV=/etc/ros_env.sh`, which sources `/etc/clearpath/setup.bash` once it exists) or use `-it ... bash`.
- `ros2 run` ignores `ROS_NAMESPACE` (only launch files honour it). Namespaced tools must pass `--ros-args -r __ns:=/$ROBOT_NAMESPACE`, which is what `robot/bin/teleop` and `camera_view` do.
- Foxglove: each robot runs `foxglove_bridge` (`robot/bin/foxglove`, whitelisted to its own namespace) on host port `8765 + slot index` (slot *i* is that robot, whatever model it runs) — connect with `ws://<host>:<port>`. foxglove_bridge 3.x speaks the `foxglove.sdk.v1` subprotocol (not `foxglove.websocket.v1`), so custom clients must request that.
- Streaming client connects to `ISAACSIM_HOST` (from `.env`) on ports 49100/tcp and 47998/udp.
- Sim tuning knobs are env vars in `.env` (`FLEET_RMW`, `ZENOH_ROUTER`, `SIM_RATE_HZ`, `PHYSICS_HZ`, `CAMERA_*`, `CAMERA_STREAMS`, `FORCE_REIMPORT`, `FLEET_DEBUG=1` for rtf/fps/pose logging, `FLEET_SETTINGS="/carb/key=val;..."` for arbitrary Kit settings). They are passed through explicitly in the `isaac-sim` service `environment:` block, so a new variable must be added there too.

## Architecture

**Robot description pipeline (host-side, one-time, per model):** `robot/config/robot.<model>.yaml.tmpl` (`a300`/`a200`/`j100`/`r100`; Clearpath config with `__NS__`/`__SERIAL__`/`__RMW__`/`__DOMAIN__` placeholders, model-specific `platform.attachments`/`sensors.camera`) → Clearpath's `generate_description` + `xacro` inside the robot image → `scripts/flatten_urdf.py` (looped over all 4 models by `scripts/gen_urdf.sh`) copies every `package://`/`file://` mesh into `sim/assets/<model>/meshes/`, rewrites paths to relative, drops `<gazebo>`/`<ros2_control>`, patches unnamed Collada materials that crash the importer, sets the USD root prim's name from `urdf_name` (so each model's own name ends up in its own USD, not a leftover hardcoded one), converts non-Blender Collada (the RealSense `d435.dae`) to a vertex-clustered OBJ (`DECIMATE_CELL`; the original has 231k triangles and cost ~30% fps) because the importer silently drops the .dae and leaves an empty Xform (invisible camera), and (`merge_visual_only_links`) folds any link that's *only* a `<visual>` (no `<collision>`, no `<inertial>` — e.g. Jackal's fender links, from `clearpath_platform_description`'s own `fender.urdf.xacro`) directly into its parent link, composing the joint+visual origins with a small hand-rolled (no numpy) rotation-matrix helper (`_origin_matrix`/`_matmul`/`_matrix_to_origin`), and re-pointing any other joint that used the removed link as *its* parent. Isaac's importer still makes a zero-mass visual-only link a genuinely separate simulated body with a PhysX fixed-joint constraint to its parent, and that constraint isn't perfectly rigid for a body this light relative to the rest of the robot — it visibly drifts away once the robot is driven or turned (confirmed live: looked fine standing still, but the fender lagged behind and detached after actually moving). Giving it a small synthetic mass/inertia instead (tried first) didn't fix this — merging the geometry away entirely, so there's no separate body left to drift, did. The fender's *orientation* itself (no rotation in the joint/visual origins) is correct as-is and untouched by this — an earlier attempt to also "fix" a supposedly-wrong orientation was based on a misreading of the drifting/detached symptom and was reverted; don't add one. Result: a self-contained URDF per model so the Isaac container needs no ROS packages. All packages needed for a200/j100/r100 (`clearpath_platform_description`, `clearpath_control`, `clearpath_generator_common`) were already installed for a300 — no new apt packages needed to add the other three.

**Real robots** (`j100_0921`/`j100_0936`, MTU's own physical Jackals): `j100_0921` generates directly from its own real `robot_data/j100_0921/robot.yaml`, unmodified — see "Real robot.yaml, used directly" below. `j100_0936` (whose own `robot_data` folder isn't currently available) still goes through `robot/config/robot.j100_0936.yaml.tmpl`, built from that robot's own real `robot_data/j100_0936/robot.yaml` (not a generic Clearpath catalog sample) the same way `j100_0921` used to, usable anywhere the 4 model codes above are (`ROBOT_MODEL_<i>` in `.env`, `MODEL_ASSETS`/`MODEL_PARAMS` in `setup_scene.py`, `scripts/gen_urdf.sh`'s `MODELS` list). Both carry each robot's actual sensor/arm loadout — a Stereolabs ZED2i stereo camera, a Microstrain IMU, dual SwiftNav Duro GPS, a Kinova Gen3 Lite arm + 2F Lite gripper, and (0936 only) a SICK LMS1xx 2D lidar — all fully simulated (real ROS2 data / real command handling), not just present as inert geometry. For `j100_0936`, `platform.extras` (the real robot.yaml's own custom `mtu32_description`/`mtu32_bringup` xacro + launch + EKF/velocity-controller overrides — MTU's own private lab packages) is dropped from the template entirely; `generate_description` succeeds cleanly without it (confirmed live), and the numeric calibration values inside it (real wheel-radius/separation multipliers, speed limits) are kept as data in `MODEL_PARAMS` instead. Two real bugs found and fixed while wiring this up originally, both in the templates themselves, not the generator (still apply to `j100_0936`'s template): (1) the real robot.yaml's `sensors.imu[0]`/`links.frame.top_shelf` both reference `parent: top_mount_link`, but nothing in the *stripped* config defines that link — only the dropped `mtu32_description` xacro did — so the template adds a substitute `links.frame` entry aliasing it to `default_mount` (Jackal's standard top-of-chassis mount point); (2) `clearpath_config`'s own hostname validator rejects underscores outright, and a real robot id like `j100_0921` (needed as `ROBOT_MODEL`) fails it two different ways — `docker-compose.yml`'s per-slot `hostname:` (the container's real OS hostname, which `clearpath_config` validates as its own default *before* even reading `robot.yaml`) is `${ROBOT_HOSTNAME_<i>:-cpr-slot-000<i>}`, where `ROBOT_HOSTNAME_<i>` (computed and kept in `.env` by `scripts/fleet.sh`, same mechanism as `ROBOT_SUFFIX_<i>` below, since compose's own interpolation can't turn underscores into hyphens) is `cpr-<model>-<serial>` with `_`→`-` (e.g. `cpr-j100-0921`, `cpr-a300-0000`) — valid by the same rule, but readable instead of a generic `cpr-slot-<i>` fallback — and each real-robot template explicitly sets `system.localhost` to the robot's own correctly-hyphenated serial (`j100_0921` → `j100-0921`) since that's what actually matters for Clearpath tooling. **ROS namespace is the robot's own id directly, no slot suffix** (`j100_0921`, not `j100_0921_0000`) — it's one specific physical robot with one fixed real identity, not a generic model needing a slot index to stay unique. `sim/scripts/setup_scene.py`'s `ROBOTS` list and `robot/entrypoint.sh`'s `ROBOT_NAMESPACE` both special-case this the same way (real robot id contains `_` → use it directly; generic model → `<model>_%04d` as before) since `docker-compose.yml` can't compute it conditionally (no string find/replace in its interpolation syntax, confirmed by testing one directly). The *docker container name* (`docker ps`/`docker exec <name>`) is fixed the same way: `docker-compose.yml`'s `container_name:` is `${ROBOT_MODEL_<i>:-a300}${ROBOT_SUFFIX_<i>-_%04d}` for every slot -- `ROBOT_SUFFIX_<i>` defaults to the usual `_%04d` (unset) but can be overridden to an *empty string* (not merely unset -- `${VAR-default}` without a colon treats those two differently, confirmed by testing directly), which `scripts/fleet.sh` does automatically, writing `ROBOT_SUFFIX_<i>=` into `.env` whenever `ROBOT_MODEL_<i>` contains `_` (and removing it again if that slot's model later changes back to a generic one) -- `docker-compose.yml` itself still can't make this decision (same "no way to inspect a variable's content" limitation as everywhere else this comes up), so it's computed in bash and handed to compose as a plain value instead. Run `scripts/fleet.sh`, not `docker compose up -d` directly, after changing a slot's model for the container name to update. Getting the corrected namespace into `docker exec` shells (`bin/teleop`/`camera_view`/`bin/rviz`, which just read `$ROBOT_NAMESPACE`) needed one more piece: `entrypoint.sh` writes the override to `/etc/robot_ns_env.sh` (freshly overwritten, not appended, so repeated container restarts never accumulate duplicate lines), which `/etc/ros_env.sh` (already sourced by every shell via `BASH_ENV`/`bashrc`) now also sources — compose's own `environment:` block provides the *stale*, slot-suffixed value to fresh `docker exec` sessions otherwise, since that's container-level config `entrypoint.sh`'s own process can't override for sessions it didn't spawn. `sim/scripts/setup_scene.py` needs three more things beyond the generic per-model pipeline: `add_camera`'s `optical_link` parameter (the ZED2i's own xacro already emits a correctly-oriented ROS optical frame, unlike the D435i models' hand-built one), a `configure_arm_drives` pass giving the arm/gripper joints real position-servo stiffness (`IMPORT_SETTINGS`' global `override_joint_stiffness=0.0` is correct for the wheels' pure velocity drive but leaves *every* joint including the arm unable to hold a commanded position at all — confirmed live: a position command barely moved it before this fix), and per-sensor OmniGraph/script-node additions in `build_ros_graph` (IMU/GPS, see their own code comments — both needed a `ScriptNode`, e.g. GPS ended up bypassing `isaacsim.ros2.bridge.ROS2Publisher`, the generic any-message publisher, entirely in favour of a plain `rclpy` publisher created directly in the script, after confirming live that a *connection* into one of that node's dynamically-created inputs silently never propagates a value even though a literal `SET_VALUES` on the same kind of attribute works fine). `j100_0936`'s 2D lidar (SICK LMS1xx) is not yet wired up (its `robot_data` folder isn't currently available to derive the real link name from), but 2D lidar itself is no longer blocked — see the "2D lidar, unblocked" paragraph below for the real, working mechanism (already live on `a200_0333`'s Hokuyo UST); RTX Lidar remains broken in this install, but is no longer the only path. Small in-place rotation commands from a standstill are also weak for these two robots specifically (same static-friction-from-rest phenomenon as Ridgeback, worse here from the arm/sensors' added rotational inertia, further limited by these two robots' own real, deliberately-honoured `max_angular=1.0` cap) — a larger command or one combined with translation works much better; a stuck-in-place robot from repeated small-rotation test attempts turned out to be accumulated test state, not a worsening bug (a `--force-recreate` and fresh test resolved it, matching this project's own established "rule out the mundane explanation first" lesson).

**Real robot.yaml, used directly (`j100_0921`):** once `mtu32_description`/`mtu32_bringup` (MTU's private lab packages `platform.extras` needs) were colcon-built and available, the stripped-template workaround for `j100_0921` was retired in favour of using `robot_data/j100_0921/robot.yaml` completely unmodified, both for host-side URDF generation and the running container's own `/etc/clearpath/robot.yaml` — no `__NS__`/`__SERIAL__`/etc. placeholder substitution at all, since the file's own baked-in `namespace: j100_0921`, `domain_id: 0`, `middleware.implementation: rmw_fastrtps_cpp` and `workspaces: [/home/robot/colcon_ws/install/setup.bash]` already match this project's conventions exactly (confirmed by inspection before relying on it). It also doesn't set `system.localhost`, so `clearpath_config`'s own default (the container's real OS hostname, `ROBOT_HOSTNAME_<i>` = `cpr-j100-0921`) is used — already valid *and* equal to this robot's own `system.hosts[0].hostname`, so no further hostname work was needed. `robot/entrypoint.sh` and `scripts/gen_urdf.sh` each gained the same branch: if a model id contains `_` and `/robot_data/<id>/robot.yaml` exists (bind-mounted read-only from the repo root into every robot container, and into `gen_urdf.sh`'s own throwaway container), `cp` it straight to the destination instead of rendering a `.tmpl`; otherwise the existing template path is unchanged (still used for `j100_0936` and the 4 generic models). `scripts/gen_urdf.sh` also colcon-builds a *separate* `sim/colcon_ws` (not the runtime `colcon_ws` the robot containers bind-mount, which already had `mtu32_description`/`mtu32_bringup` built) and sources its `install/setup.bash` before calling `generate_description`, so the host-side one-shot generation pass has the same package available. Two things this actually fixed, not just avoided: `top_mount_link` is now genuinely defined by `mtu32_description`'s own xacro (real mesh + collision, parented on `default_mount`), so the old substitute `links.frame` alias (`top_mount` → `default_mount`) is gone entirely — there's no more fake link to alias; and the new xacro also unconditionally adds a second camera body, `camera_1` (a RealSense D405 on `arm_0_end_effector_link`) — inert geometry only, since `sensors.camera`'s `intel_realsense` entry is still commented out in the real robot.yaml, so no new ROS publishing is implied. **One real bug found and fixed in `scripts/flatten_urdf.py`'s `dae_to_obj`** while converting `top_mount_link`'s mesh (`top_assy_rev1.dae`, 535k triangles, a hand/CAD Collada export like the D435i's — see `dae_to_obj`'s own docstring): it remapped *every* index in a `<triangles>` element's interleaved `<p>` list through the position-vertex `remap` table before slicing out just the VERTEX-offset ones, so a NORMAL index numerically larger than the vertex count threw `IndexError` — `d435.dae` happened to index normals 1:1 with positions, masking this. Fixed by slicing to the VERTEX input's own `offset` *before* remapping. Since `top_mount_link` now has real collision (unlike the old fake alias), `merge_visual_only_links`' cascading merge for the IMU sensor chain (`imu_1_link`/`imu_1_base_link`, both visual-only) now stops at `top_mount_link` instead of continuing all the way to `chassis_link` — confirmed in the actual flattened URDF (no `imu_1` string survives; `top_shelf_link`'s own joint parent is `top_mount_link` directly), so `MODEL_PARAMS["j100_0921"]["imu_link"]` changed from `"chassis_link"` to `"top_mount_link"` accordingly (re-verified live afterward: real, gravity-consistent `linear_acceleration.z ≈ 9.8`, not zero/garbage). `chassis_link` itself is unaffected (still `base_link` — re-confirmed by a successful drive test with no "Articulation controller failed" error, the same live check this project always uses rather than assuming). `camera_optical_link`/`gps_links`/`has_arm` are unaffected too, since they come from `clearpath_sensors_description`'s own sensor macros, unrelated to `mtu32_description`. `robot_data/` and `sim/colcon_ws/` are both `.gitignore`d (large, private lab material, same reasoning as the existing `colcon_ws/build|install|log` entries). **Known follow-up, not chased in this pass**: `top_assy_rev1.obj`'s 535k triangles barely reduce under the existing `DECIMATE_CELL` (0.001 m) — a much heavier asset than anything else in this project's models — worth a dedicated fps check and possibly a coarser decimation cell for this specific mesh if it turns out to cost meaningfully more than the D435i's own (already-tuned) 17k-triangle budget.

**Two more real robots (`a200_0333`, `a300_00036`), same pipeline, no private-package dependency:** unlike `j100_0921`, neither references any private package (`a200_0333`'s `platform.extras.urdf` is an empty `{}`; `a300_00036` has no `extras` key at all), so `generate_description` succeeded first try with no workaround needed. `a200_0333` carries a real D435 camera (not D435i — mounted via `sensors.camera` + a `mounts.fath_pivot` adapter, a Clearpath mount type not seen elsewhere here, but still produces the same `camera_0_link` name `add_camera`'s existing default hand-built-optical-frame path already expects, so no `camera_optical_link` override needed) plus a Hokuyo UST 2D lidar and a Velodyne VLP16 3D lidar (both simulated — see "2D lidar, unblocked" and "3D lidar" below). `a300_00036` carries only a real Phidgets Spatial IMU and **no camera at all** — the first model with none, which needed a new `has_camera` `MODEL_PARAMS` flag (default `True`) to guard `add_camera`/`build_ros_graph`'s camera wiring in `main()`'s spawn loop, since `find_prim` would otherwise raise looking for a nonexistent `camera_0_link`. Two real upstream bugs found and fixed in `scripts/flatten_urdf.py` converting `a200_0333`'s Velodyne meshes (`velodyne_description`'s own shipped `.dae` files, unrelated to this project): (1) they use the literal unescaped string `<STL_BINARY>` as a Collada node id/name, invalid XML, fixed with a narrow text substitution before parsing; (2) once parseable, `dae_to_obj` only ever handled `<triangles>`, but these STL-derived meshes use `<polylist>` instead (confirmed all-triangle via `<vcount>`) — fixed by extending the face-extraction loop to handle both, fan-triangulating `<polylist>` correctly for the general n-gon case too. **`a300_00036` needed the same `chassis_link` fix as a200/j100's own precedents**: the real robot.yaml's Phidgets IMU (parent: `base_link`, visual-only) merges into `base_link`, giving it real visual content it didn't have in the generic a300 model — enough to flip the importer's articulation root there too (hit "Articulation controller failed" at runtime with generic a300's own `chassis_link="chassis_link"`, no import-time warning); fixed with `chassis_link="base_link"`, re-verified via a clean drive test.

**2D lidar, unblocked:** `isaacsim.sensors.experimental.physics.Raycast`/`RaycastSensor` is a real, working, per-physics-step PhysX raycast sensor — the same module `IMU`/`IMUSensor` already use successfully, with its own independent `IRaycastSensor` C++ interface, entirely unrelated to the broken `isaacsim.sensors.rtx` pipeline. `LIDAR2D_READ_SCRIPT` authors one as a plain child of the real `lidar2d_link` prim (inheriting its mount pose automatically, same pattern `add_camera` uses) with a ray fan matching the real sensor's declared FOV (`LIDAR2D_ANGLE_MIN/MAX` ±2.356 rad, `LIDAR2D_NUM_RAYS` 541 — ~0.5° resolution, an approximation, not either real sensor's exact spec), and publishes `sensor_msgs/LaserScan` via a plain rclpy publisher (same reasoning as `GPS_READ_SCRIPT`: a per-tick computed reading, not a literal `SET_VALUES` case). **Real bug found in this "experimental"-namespace API itself**, isolated through a sequence of targeted single/few-ray tests rather than assumed: `get_data()['depths']` does not report a genuine per-ray distance — a 3-ray down/forward/up probe returned `depths=[0.1, 0.1, 0.1]` (exactly `min_range`) for all three regardless of what each ray actually hit, while the *same reading's* `hit_positions` were correct per ray (`[0,0,-0.1]`, a real close hit; `[3.77,0,0]`, a real hit on scene geometry; `[0,0,0]`, a genuine miss). Worked around by computing each ray's range as the Euclidean norm of its own `hit_positions` entry instead of trusting `depths` at all (`output_frame="SENSOR"`, the default, keeps `hit_positions` in the same local frame as `ray_origins`, so the norm is directly the range in metres); a `[0,0,0]` entry means no hit, remapped to `+Inf` per REP-117. Verified live on `a200_0333`'s Hokuyo: genuine, varied finite ranges (209/541 rays hit something, 1.36–9.99m, matching the scene's own known target-box/wall geometry), not a uniform placeholder.

**3D lidar:** the same `Raycast`/`RaycastSensor` mechanism, extended to `a200_0333`'s real Velodyne VLP16 (16 channels, real ±15° vertical FOV, 360 horizontal steps — 5760 rays total, publishing `sensor_msgs/PointCloud2` on `sensors/lidar3d_0/points` instead of `LaserScan`), reusing the same `hit_positions`-based range fix 2D lidar needed (the `depths` bug applies here too). **The very first attempt segfaulted the whole `a300-isaac-sim` container** (`Exited (139)`) — a real crash, not silently ignored: immediately disabled the new code and confirmed the rest of the fleet still came up cleanly before investigating further. Root cause, found by actually reading the log line just before the crash rather than assuming it was the 5760-ray count: `UsdStage::_ValidateEditPrimAtPath ... authoring to an instance proxy is not allowed` — `a200_0333`'s `sensor_arch` mount subtree (the VLP16's own real ancestor chain, unlike 2D lidar's non-instanced bracket mount) is USD-instanceable, so authoring the sensor prim as its child is rejected outright; the retry-on-exception pattern (safe for a genuinely transient "not ready yet" condition, which is all IMU/2D lidar ever hit) instead kept re-attempting the same permanently-failing call every tick against an instance proxy, which is what actually crashed the process. Fixed by parenting the raycast sensor under `chassis` instead (never instanced) and computing `lidar3d_link`'s real pose *relative to chassis* once, live, via `UsdGeom.Xformable(...).ComputeLocalToWorldTransform()` on both prims (a static offset, since both are real rigid links) — passed to `Raycast.create()` as explicit `translations`/`orientations` rather than relying on parent-child nesting. Retested the exact same 5760-ray configuration after the fix and it's completely safe — confirmed ray count was never the actual problem by testing incrementally back up to it (576→1152→3200→4800→5760, each a clean boot with real point data) rather than just assuming a smaller value was the necessary fix. `FLEET_DEBUG=1`: `render_fps` 12.1→10.4 with 3D lidar added on top of 2D lidar (~14% cost, not isolated from the scene's already camera-bound baseline).

**`j100_0922`, `j100_0921`'s twin minus the arm — one real bug, one real physics finding:** identical to `j100_0921`'s own real robot.yaml except its whole `manipulators:` section is commented out (no arm/gripper). `mtu32_description`'s own xacro unconditionally mounts a second camera (`camera_1`, a RealSense D405) on `arm_0_end_effector_link`, assuming every Jackal running it has the Kinova arm — with none configured here, that link is never defined, leaving `camera_1`'s mount joint (and, once that's removed, its own now-orphaned child joint) referencing links that don't exist anywhere in the URDF. `scripts/flatten_urdf.py` gained a general (not `j100_0922`-specific) `prune_dangling_joints` pass, run before `merge_visual_only_links`, that drops any joint whose `<parent>` was never actually defined as a link, cascading to catch newly-orphaned joints too. `chassis_link`/`imu_link`/etc. are otherwise identical to `j100_0921`'s (re-verified live, not assumed). **Real, reproducible physics finding, not chased into a fix**: `j100_0922` visibly wheelies (pitches up on its rear wheels) under even a gentle drive command — verified real (a fresh, isolated, uncommanded spawn is perfectly level; a single `drive_test.py 0.15 0 1.5` reproducibly pitches it to the exact same ~77° orientation each time, not settling noise). Likely cause, not fully confirmed: genuinely lighter than `j100_0921`/`j100_0936` without the arm's own real mass at the rear, so the same wheel-drive torque that's gentle on every other real robot here produces a much larger pitching moment on this one. Left as a known characteristic pending direction on which lever to pull (wheel damping, command ramping, or just documenting it) — see `last_session.md`'s own addendum for the investigation.

**Sim (`sim/scripts/setup_scene.py`, run via `--exec` in the Isaac streaming app; `./sim` is mounted at `/sim`):**
1. URDF → USD import, cached per model in `sim/generated/<model>/` and invalidated by a stamp file (`.import_stamp`: import settings + URDF mtime/size) or `FORCE_REIMPORT=1`. The importer output path is fragile — the script deletes each model's `usd_dir` first so it doesn't write `<model>_1/`, `<model>_2/`, ….
2. Builds the world, spawns `NUM_ROBOTS` robots (`ROBOTS = [(f"{model}_{i:04d}", model) for ...]`, from `ROBOT_MODELS` — a comma list from compose, one entry per slot; spaced along Y and centred; props and the viewport scale with the count), adds a D435i USD camera, and builds one OmniGraph per robot using `isaacsim.ros2.bridge` nodes: `cmd_vel` → differential drive → wheel velocity drives; publishes `platform/odom`, `platform/joint_states`, TF, and camera color/depth + camera_info. Topics are relative and land under each robot's namespace. Each distinct model's URDF→USD import (`import_urdf_if_needed`, per-model paths in `MODEL_ASSETS`) runs once regardless of how many robots use it.
3. Time: the stage runs at `SIM_RATE_HZ` (compose fallback 20; this repo's tracked `.env` currently has 22, tuned for its 2-robot/FastDDS/async-rendering setup — treat it as a value to retune, not a constant). Set it to about the `render_fps` that `FLEET_DEBUG=1` reports, since rtf = fps / SIM_RATE_HZ (~15 for 3 robots on zenoh, ~10 for 5). PhysX substeps at `PHYSICS_HZ` (60) inside each frame, because camera rendering per robot is too costly for 60 Hz frames. Keep real-time factor ≈ 1.0 (check with `FLEET_DEBUG=1`). The frame rate is also the WebRTC stream's frame rate. Measured levers (see README *Faster streaming*): `/app/asyncRendering=true` (+~20%, set via `FLEET_SETTINGS` in `.env`), fewer robots, `CAMERA_STREAMS=none`; resolution, streams, render mode, UI hiding and viewport size (`FLEET_VIEWPORT_RES`) don't change the fps because each camera render product has a fixed ~15–20 ms cost. `FLEET_MERGE_FIXED=1` does not work: it merges away `camera_0_link` and the scene build fails.
4. Drive constants live in `MODEL_PARAMS` (one entry per model: `wheel_radius`, `wheel_separation`, `separation_multiplier`, `max_linear`, `max_angular`, `chassis_link`), copied from each model's real `clearpath_control/config/<model>/control/diff_4wd.yaml` — keep them in sync with the real configs. `chassis_link` is the one URDF link the drive/odometry OmniGraph targets (`DriveFront`/`DriveRear`/`Odom.inputs:chassisPrim`) — it must be a prim the importer actually gave `UsdPhysics.ArticulationRootAPI`, **not just whichever link looks like "the chassis"**, and re-checked (not assumed) after *any* change to a model's URDF shape: a300/r100 each have one direct fixed-jointed child of `base_link` that becomes the root, so it's literally called `chassis_link`; a200's `base_link` has several direct children with no single obvious one, so the importer roots the articulation at `base_link` itself (targeting a200's own `inertial_link`, the one that actually carries mass by URDF `<inertial>` inspection, instead fails with an OmniGraph "Articulation controller failed" error at runtime with **no import-time warning**). j100 used to be a `chassis_link` case like a300/r100, until `merge_visual_only_links` (see above) started folding its fenders into `base_link`, which alone was enough to flip its articulation root to `base_link` too, exactly like a200 — caught by re-running the same drive test after that unrelated-looking change, not by inspection. **Running all 4 distinct models in one sim (4 robots, no repeats) reproduced a `PhysX Internal CUDA error` crash** on the dev machine; every single model alone and every combination of ≤3 distinct models tested fine — not root-caused, flagged in the README as a known issue rather than chased further.

Ridgeback (r100) is Clearpath's holonomic mecanum platform and drives omnidirectionally: forward/back and rotation use the same `diff_4wd.yaml` OmniGraph as the other models (`Diff`/`DriveFront`/`DriveRear`, built for every model regardless of `drive`), and a `BodyDrive` script node (`omni.graph.scriptnode.ScriptNode`, added only when `MODEL_PARAMS[model]["drive"] == "omni"`) separately patches in real sideways (linear.y) motion every tick by reading the chassis articulation's *current* velocity (`isaacsim.core.experimental.prims.Articulation.get_velocities`/`set_velocities`, which act on a floating-base articulation's root — the same root `chassis_link` already has to be for the drive/odometry OmniGraph), decomposing it into the chassis' own body frame, replacing just the lateral component with the commanded `vy`, and writing the recomposed world-frame velocity back, leaving angular velocity untouched entirely. This two-part design exists because a straight port of Clearpath's real mecanum kinematics doesn't work in this sim: `isaacsim.robot.wheeled_robots.HolonomicController` (the obvious tool, and Isaac's genuinely-correct QP-based mecanum solver — `mecanumAngles` derived and verified against `omni_4wd.yaml`'s own `sum_of_robot_center_projection_on_X_Y_axis`) computes the right per-wheel speeds, but Ridgeback's own URDF gives every wheel a **plain cylinder `<collision>`** (the angled-roller detail is mesh-only, in `<visual>`), and this PhysX version has no anisotropic/directional friction (`frictionType` is fixed to `"patch"`, checked directly in the PhysX schema) to fake a roller's passive sideways slip — a spinning cylinder cannot produce sideways thrust no matter what any kinematic layer computes, confirmed live (wheels visibly spun correctly, robot barely crept while commanded to strafe). Driving those wheel joints with the (correctly computed) mecanum speeds anyway, purely for cosmetic spin, made rotation actively *wrong* — real, substantial reaction torque through the wheel joints fought the chassis's actual motion — so the wheel joints are left undriven for Ridgeback's lateral component and it doesn't visually spin its wheels while strafing. **Known limitation, found the same way both times it was tried (a full velocity override and, later, real diff-drive wheels for rotation):** a small *pure* in-place rotation command from a standstill (0.5 rad/s alone, verified live) is almost entirely absorbed — PhysX's contact solver resists breaking static friction to scrub a stationary wheel sideways far more than it resists continuing an already-sliding motion — while a larger command (2.0 rad/s) or one combined with any translation comes through close to correctly. Real wheel rolling for rotation was kept anyway (it's at least as effective as a direct override, and keeps rotation on the same already-proven code path as the other 3 models).
5. `build_world()` also adds static scene dressing: target boxes/wall/pillars (with colliders), and three `add_lavender()` plants referencing `sim/assets/lavender/SM_Lavender_Nanite_01.usd` (`instanceable=True`, scaled ×0.01 to convert the asset's cm units to this stage's metres — USD does not do this automatically across a reference boundary). ~1.26M triangles per plant; costs ~3-4 fps for the 3 of them. They render dark under the scene's current light intensities (fine under brighter light, which was not made the default because it overexposes everything else).

**ROS workspace:** every robot image has a `robot` user, created by renaming the base image's existing uid/gid 1000 `ubuntu` account (Ubuntu 24.04 ships one; reusing its uid avoids a clash and matches the typical host uid, so the bind mount below needs no chown gymnastics). `/home/robot/colcon_ws` is bind-mounted from the single host directory `./colcon_ws` into every robot container (the `x-robot` volumes anchor), so it's the same workspace everywhere and on the host, not a copy per robot. The container's main process is still root (the entrypoint writes `/etc/clearpath/robot.yaml` and runs the background services below); `robot` exists only for `docker exec -u robot -it <robot> bash` workspace/colcon work. It's wired into `/etc/clearpath/setup.bash` via `robot.yaml`'s own `workspaces` field (see below), so it's sourced the same real way on a Clearpath robot, not just via the system-wide bashrc fallback.

**Robots (`robot/`):** `entrypoint.sh` does the following at container start, mirroring a real robot's boot as closely as the installed Clearpath packages allow:
- renders `/etc/clearpath/robot.yaml` from `/opt/clearpath/robot.${ROBOT_MODEL:-a300}.yaml.tmpl` (`ROBOT_MODEL` set per compose slot, default a300) using `ROBOT_NAMESPACE`, `RMW_IMPLEMENTATION` (`FLEET_RMW`) and `ROS_DOMAIN_ID`, written to `system.ros2.{middleware.implementation,domain_id}`; the serial is the namespace with `_` → `-`, since Clearpath hostnames can't contain underscores. The template's `system.ros2.workspaces` also names `/home/robot/colcon_ws/install`.
- runs `ros2 run clearpath_generator_common generate_bash -s /etc/clearpath` — the actual tool a real robot's systemd units run — which reads that `robot.yaml` and writes `/etc/clearpath/setup.bash` (sources ROS, then `colcon_ws/install/setup.bash`, then exports `ROS_DOMAIN_ID`/`RMW_IMPLEMENTATION`/discovery settings from the yaml). Before this runs, the entrypoint makes sure `colcon_ws/install/setup.bash` exists (a one-line placeholder if nothing's been built there yet — `colcon build`/`scripts/colcon_build.sh` overwrite it with the real one), so a workspace with nothing in it yet never breaks sourcing.
  - `clearpath_generator_common` in this apt package only exposes `generate_description` (used host-side, see above), `generate_bash` (used here) and `generate_discovery_server`/`generate_vcan`/`generate_zenoh_router`/`moveit_collision_updater` as *console_scripts* — none of the latter apply to a simulated robot with no CAN bus, one shared `zenoh-router`, or (`moveit_collision_updater`, i.e. `generate_semantic_description`) a working collision model in this setup — it crashes with an Eigen assertion here, and isn't run. Its own `ParamGenerator`/`LaunchGenerator` Python classes (unwrapped in any console_script) are genuinely real for platform/manipulators but leave `generate_sensors()` abstract (`NotImplementedError`) and `LaunchGenerator` fully abstract — **superseded** by `clearpath_generator_robot` below, which this project now builds from source specifically to close that gap, rather than treated as a permanent limitation.
  - **`robot/bin/generate_params`** (run once at boot alongside `generate_bash`, after sourcing both `/etc/clearpath/setup.bash` and the `/opt/clearpath_robot_ws/install/setup.bash` overlay — see Dockerfile): calls `clearpath_generator_robot.param.generator.RobotParamGenerator` and `.launch.generator.RobotLaunchGenerator` (each `.generate()`, which covers sensors+platform+manipulators in one call — confirmed by reading the real base class's own `generate()` aggregate). `clearpath_generator_robot` is the real per-robot generator a physical Clearpath robot's bringup runs, source-only (`github.com/clearpathrobotics/clearpath_robot`, jazzy branch — **not** in the public apt repo, only `clearpath_generator_common` is), found after the user pointed at the `clearpath_robot` package name directly rather than trusting the earlier "sensors gap, not chased further" conclusion. `robot/Dockerfile` clones it at build time and `colcon build`s just two of its six packages into a separate `/opt/clearpath_robot_ws` overlay: `clearpath_generator_robot` itself, and `clearpath_sensors` (default per-sensor-type param/launch templates — `RobotParamGenerator`/`RobotLaunchGenerator` read these via `get_package_share_directory('clearpath_sensors')`, so both are required, not just the first). The other four packages in that repo (`clearpath_robot` metapackage, `clearpath_hardware_interfaces`, `clearpath_motor_drivers`, `clearpath_tests`) are real-motor-controller/CAN-hardware-only and not built. Both packages' `package.xml` list many genuinely-unavailable hardware/sensor-driver `exec_depend`s (`clearpath_hardware_interfaces`, `micro_ros_agent`, `realsense2_camera`, `velodyne_driver`, `zed_wrapper`, ...) — confirmed harmless: **`colcon build` never verifies `exec_depend`s**, only `build_depend`s (neither package.xml declares any), and the actual generator code only imports `clearpath_config`/`clearpath_generator_common`/its own modules. Verified live across all 4 currently-configured real robots: `j100_0921`/`j100_0922` each get real `camera_0.yaml`+`imu_1.yaml` (ZED2i + Microstrain IMU; GPS correctly omitted, both `swiftnav_duro` entries have `launch_enabled: false`), `a300_00036` gets `imu_0.yaml` only (Phidgets Spatial, no camera), `a200_0333` gets `camera_0.yaml`+`lidar2d_0.yaml`+`lidar3d_0.yaml` (D435, Hokuyo UST, Velodyne VLP16) — each with a matching `launch.py`, plus a `platform/config/control.yaml` whose `diff_drive_controller` parameters independently match this project's own hand-derived `MODEL_PARAMS` values exactly, a nice cross-check. **Caveat, not silently left implicit**: actually running those launch files would not integrate with this project's own drive/sensor pipeline — `platform-service.launch.py`'s `control.launch.py` expects a real `ros2_control` hardware interface plugin, which doesn't exist here (wheels are driven directly by OmniGraph nodes into Isaac's PhysX joint drives, bypassing ros2_control entirely) and every generated launch file defaults `use_sim_time=false` (the base `LaunchGenerator.__init__` hardcodes it), so running them as-is wouldn't move the robot and would likely collide over shared topic names (`platform/odom`, `platform/joint_states`, `cmd_vel`, the real sensor driver topics) with what already works. For inspection/reference — real Clearpath output the user can read or run standalone later — not a drop-in replacement for this project's own OmniGraph-based pipeline.
  - **Known upstream quirk (installed `clearpath_generator_common` 2.9.15):** its bash generator builds the workspace source line with `workspace.strip('setup.bash')` — Python's character-set `str.strip`, not a substring removal — which mangles most spellings of a workspace path (e.g. `.../colcon_ws` → `.../colcon_w`). The template's `/home/robot/colcon_ws/install` happens to be immune (no leading/trailing characters in `"setup.bash"`'s character set to strip) and is the only value confirmed to produce the correct `source .../install/setup.bash` line; do not "clean up" that path without re-checking against this bug.
  - **Minor, harmless, self-healing:** `/etc/clearpath/setup.bash` is generated once at container start (or `restart`, which re-runs the entrypoint but keeps the container's own filesystem, including a previous boot's `/etc/clearpath/setup.bash`) and unconditionally sources `colcon_ws/install/setup.bash`. If you delete `colcon_ws/install/` on the host while a container keeps running, any `docker exec` shell started in that window (its `BASH_ENV` re-evaluates `/etc/ros_env.sh`, which finds the stale `/etc/clearpath/setup.bash` and sources it) prints one `No such file or directory` line for that source command and continues — everything after it (`ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`, …) still gets set. It resolves itself as soon as something rebuilds the workspace.
- sources the generated `/etc/clearpath/setup.bash` and sets `ROS_NAMESPACE` (only honoured by launch files, but harmless to set; `ros2 run` tools still need `--ros-args -r __ns:=`, see `bin/teleop`).
- starts two restarting background services: `robot_state` (regenerates the URDF from `robot.yaml` and runs `robot_state_publisher` under the namespace, giving the full TF tree plus `/<ns>/robot_description`) and `foxglove` (the bridge).

The sim itself only publishes `odom→base_link` and `camera_0_link→camera_0_color_optical_frame`, so URDF link/joint names must match the USD's; wheel joints come from `platform/joint_states`. The `teleop`, `camera_view` and `rviz` wrappers in `robot/bin/` are installed to `/usr/local/bin` and are model-agnostic (they only read `$ROBOT_NAMESPACE`).

Robot services in compose share the `x-robot` anchor; compose defines eight robot service **keys** `robot0`…`robot7` (stable, model-agnostic — never typed by a user), each with `container_name`/`hostname`/`ROBOT_NAMESPACE`/`ROS_NAMESPACE` interpolated as `${ROBOT_MODEL_<i>:-a300}_%04d` for its fixed index *i* (e.g. slot 1 with `ROBOT_MODEL_1=j100` becomes `j100_0001`) and `ROBOT_MODEL: ${ROBOT_MODEL_<i>:-a300}` in its environment. Slot *i* has the profiles `n<k>` for every k > i, and `.env` sets `COMPOSE_PROFILES=n${NUM_ROBOTS}` (compose interpolates inside `.env`, and a shell `NUM_ROBOTS` overrides it), so `NUM_ROBOTS=N` starts exactly the first N. The `isaac-sim` service gets `ROBOT_MODELS` = all 8 `${ROBOT_MODEL_<i>:-a300}` values comma-joined; the sim only uses the first `NUM_ROBOTS` of them, zipped with its own derived slot-index namespaces — so both sides can't disagree on naming even though compose and the sim compute it independently. Ports/hostnames are fixed per slot index (Foxglove `8765+i`) regardless of model. Compose does not stop services of inactive profiles when the count is lowered (`--remove-orphans` doesn't either), hence `scripts/fleet.sh`, which removes surplus slots via `docker compose rm -sf robot<i>` (the stable service key, not a guessed container name — correct regardless of which model that slot last ran) and reads real slot names back one at a time via `docker compose ps --format '{{.Name}}' robot<i>` for its status line (batch-querying several service names at once returns them alphabetically, **not** in argument/slot order — found by testing, not assumed). Going beyond 8 means copying a service block and raising `MAX` in `fleet.sh`.

**Networking / middleware:** sim and robots share the private `ros` bridge network. `FLEET_RMW` in `.env` (deliberately not `RMW_IMPLEMENTATION`, which a ROS-configured host shell would export over `.env`) picks `rmw_zenoh_cpp` (compose fallback if `.env` omits it) or `rmw_fastrtps_cpp` for every container via the `x-rmw-env` anchor. The tracked `.env` currently pins `rmw_fastrtps_cpp` — a runtime choice made while investigating streaming performance, not a change of the intended default. The image tag is `clearpath-robot:jazzy` (renamed from `a300-robot:jazzy` once it started serving 4 models) and the compose project is `clearpath-fleet` (was `a300-fleet`); `docker compose down` under the old project name/file won't find containers created under the new one and vice versa — clean up stragglers with plain `docker rm -f`/`docker network rm` if switching between very old and current checkouts of this repo.
- zenoh: all sessions run in **client** mode (`ZENOH_CONFIG_OVERRIDE`) against the single `zenoh-router` service. The default `peer` mode fails across containers because peers only listen on loopback. `ZENOH_ROUTER` can point at an external router.
- Isaac Sim's bundled ROS libs only have Fast DDS/Cyclone, so `docker/isaac-sim.Dockerfile` adds system ROS 2 Jazzy + rmw_zenoh_cpp; `docker/isaac-entrypoint.sh` sources it only when `FLEET_RMW=rmw_zenoh_cpp` (Isaac then loads the system ROS instead of its internal one). Zenoh costs ~3–4 fps in the sim relative to FastDDS, so lower `SIM_RATE_HZ` when using it (~15 gave rtf ≈ 0.95 for 3 robots).
- FastDDS: UDP only (`docker/fastdds_udp.xml`, mounted into every container); shared-memory transport must stay disabled because containers don't share `/dev/shm`.
All containers must have the same `ROS_DOMAIN_ID`. `volume-init` chowns the named volumes to uid 1234 (Isaac Sim's user) before the sim starts.
