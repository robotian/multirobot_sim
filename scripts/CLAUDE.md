# scripts/ — robot description pipeline

Moved out of the root CLAUDE.md (loads when working under this directory; the root file links here).

**Robot description pipeline (host-side, one-time, per model):** `robot/config/robot.<model>.yaml.tmpl` (`a300`/`a200`/`j100`/`r100`; Clearpath config with `__NS__`/`__SERIAL__`/`__RMW__`/`__DOMAIN__` placeholders, model-specific `platform.attachments`/`sensors.camera`) → Clearpath's `generate_description` + `xacro` inside the robot image → `scripts/flatten_urdf.py` (looped over all 4 models by `scripts/gen_urdf.sh`) copies every `package://`/`file://` mesh into `sim/assets/<model>/meshes/`, rewrites paths to relative, drops `<gazebo>`/`<ros2_control>`, patches unnamed Collada materials that crash the importer, sets the USD root prim's name from `urdf_name` (so each model's own name ends up in its own USD, not a leftover hardcoded one), converts non-Blender Collada (the RealSense `d435.dae`) to a vertex-clustered OBJ (`DECIMATE_CELL`; the original has 231k triangles and cost ~30% fps) because the importer silently drops the .dae and leaves an empty Xform (invisible camera), and (`merge_visual_only_links`) folds any link that's *only* a `<visual>` (no `<collision>`, no `<inertial>` — e.g. Jackal's fender links, from `clearpath_platform_description`'s own `fender.urdf.xacro`) directly into its parent link (recorded in `sim/assets/<model>/merged_links.json`, merged link -> link it now lives in, which `setup_scene.py` uses to find a merged sensor frame such as the IMU's), composing the joint+visual origins with a small hand-rolled (no numpy) rotation-matrix helper (`_origin_matrix`/`_matmul`/`_matrix_to_origin`), and re-pointing any other joint that used the removed link as *its* parent. Isaac's importer still makes a zero-mass visual-only link a genuinely separate simulated body with a PhysX fixed-joint constraint to its parent, and that constraint isn't perfectly rigid for a body this light relative to the rest of the robot — it visibly drifts away once the robot is driven or turned (confirmed live: looked fine standing still, but the fender lagged behind and detached after actually moving). Giving it a small synthetic mass/inertia instead (tried first) didn't fix this — merging the geometry away entirely, so there's no separate body left to drift, did. The fender's *orientation* itself (no rotation in the joint/visual origins) is correct as-is and untouched by this — an earlier attempt to also "fix" a supposedly-wrong orientation was based on a misreading of the drifting/detached symptom and was reverted; don't add one. Result: a self-contained URDF per model so the Isaac container needs no ROS packages. All packages needed for a200/j100/r100 (`clearpath_platform_description`, `clearpath_control`, `clearpath_generator_common`) were already installed for a300 — no new apt packages needed to add the other three.

**Deploying to a real robot (`scripts/deploy_robot.sh <id>`):** two workspaces on the robot, both listed in its `/etc/clearpath/robot.yaml` `system.ros2.workspaces` (sourced in order, later ones override): `~/robot_ws` first, then any others (a300_00036: `~/mocap4r2_ws`), then `~/colcon_ws` last. `~/robot_ws` holds the robot's own packages (hardware drivers, Kinova, ZED, gripper, ...: what differs per robot), built by hand on the robot (`colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release`), with a `COLCON_IGNORE` in each package this repo's `colcon_ws/src` provides (also listed in that repo's `.git/info/exclude`). `~/colcon_ws` is exactly `colcon_ws/src` (rsync `--delete`, no `.git`, `-c` checksums), built by the script on the robot with the workspaces before it in robot.yaml as underlays. A package an underlay workspace (not `/opt/ros`) still builds is the robot's own: the script doesn't build this repo's copy there (`--packages-ignore`, printed as "not built") and removes what an earlier deploy built of it; `COLCON_IGNORE` it in `robot_ws` to use this repo's. Same-named packages can differ completely: `swiftnav_ros2_driver` here is a messages-only stand-in (just `Baseline.msg`, so `duro_sim`/`dual_duro_heading` build in the sim), on the robot it's Swift Navigation's driver (`sbp-to-ros`, needs `~/libsbp`) with the identical message; overriding it with the stand-in broke `clearpath-platform-extras` ("libexec directory ... does not exist"). It refuses a dirty `colcon_ws/src` (submodules included) unless `--allow-dirty`, shows a dry run and asks before deleting anything, writes `~/colcon_ws/DEPLOYED` (commit + submodule commits), and restarts nothing. **Edits on the robot:** `~/colcon_ws/src` there has no `.git`, and rsync would silently overwrite an edited file, so each deploy saves `~/colcon_ws/.deployed_manifest` (sha1 per file, `.git`/`__pycache__` skipped) and the next one first compares the robot's files with it: anything changed/added/removed there stops the deploy (`--dry-run` just lists it). `--pull` copies those into `colcon_ws/src` and deploys nothing (a file also changed here since the deploy goes to `<file>.robot`; a removal is applied only if the file is unchanged here), then makes the robot's current files the new baseline; `--force` overwrites them. Building on the robot writes nothing into `src` (checked), so any difference is a real edit. Host default `cpr-<id, _→->.local` (mDNS; the plain hostnames in robot.yaml don't resolve from the lab network, and their IPs there are stale); needs key login (`ssh-copy-id robot@<host>`).

a300_00036 (2026-10-05): its old workspace is `~/colcon_ws_backup` (keep it); `~/robot_ws/src` is a copy of its `src` with COLCON_IGNORE in apriltag_ros, depthimage_to_laserscan, docking_utils, dual_duro_heading, husky_operations_manager, laser_filters, mocap_fake_localizer, mtu32_husky (33 packages left). The robot keeps its own `status_interfaces` (image_detection / unloader_server / kinova_task_manager depend on it, and an underlay can't depend on its overlay; same messages as this repo's) and `swiftnav_ros2_driver` (the real driver). `image_detection/.venv` was created under the old `~/colcon_ws/src`: its `bin/activate`, `pip` and `onnxruntime_test` were rewritten to `~/robot_ws/...` (the nodes find it from the package prefix via `venv_bootstrapper.py`). `~/mocap4r2_ws` was built while the old `~/colcon_ws` existed, so its setup.bash also sources `~/colcon_ws` (harmless; rebuild it over robot_ws only to clean up). The Clearpath forks there (clearpath_common/config/robot, gen3_lite_custom_gripper) were already COLCON_IGNOREd: the robot runs Clearpath's apt packages. robot.yaml backup before the workspaces change: `~/robot.yaml.2026-10-05-172030.bak`.

**Real robot middleware (2026-10-07, tested on a300_00036 against the base station):**
- **Zenoh router config** (`scripts/zenoh_router_config.py`): `ssh robot@<ip> python3 - [wifi_if] < scripts/zenoh_router_config.py` writes `~/zenoh_config/router.json5` there (rmw_zenoh_cpp's default config + `downsampling` on egress of the WiFi interface, default `wlp3s0`: the arm's `controller_manager` introspection/statistics 1 Hz, `controller_state` 10 Hz, `camera_0`/`camera_1` `color/compressed` 10 Hz). Then add `profile: /home/robot/zenoh_config/router.json5` under `system.ros2.middleware` in `/etc/clearpath/robot.yaml` (saving it restarts the services): Clearpath's generated `zenoh-router-start` exports it as `ZENOH_ROUTER_CONFIG_URI` (installed `clearpath_generator_common` 2.9.15; `setup.bash` also exports it as `FASTRTPS_DEFAULT_PROFILES_FILE`, harmless under zenoh -- remove the line before switching the robot to Fast DDS). The profile replaces the whole router config. Check a new config with a throwaway router first: `ZENOH_ROUTER_CONFIG_URI=<file> ZENOH_CONFIG_OVERRIDE='listen/endpoints=["tcp/127.0.0.1:17447"]' timeout 5 ros2 run rmw_zenoh_cpp rmw_zenohd`. Verified: off the robot those topics arrive at 1 / 10 / ~8.5 Hz, the robot's own nodes keep full rate (the controller_manager topics are ~1 kHz, ~10 MB/s together on a300_00036). a300_00036 runs it (robot.yaml backups `~/robot.yaml.*.bak`; its file predates the `<topic>/*/*` patterns, which keep `image_raw` from also matching `image_raw/zstd`, same effect there). a200_0284 too since 2026-10-07 (`wlo1`; its Kinova wrist camera sent ~19 MB/s under an RViz-like load, now raw images/points 2 Hz, zstd/compressed 10 Hz): over 10 min of subscribe bursts, windows with a >1 s gap went from 15 to 6 and burst-time rates from 7-30/s to 31-40/s.
- **Remote zenoh sessions must be clients** (`ZENOH_CONFIG_OVERRIDE='mode="client";connect/endpoints=["tcp/<robot>:7447"]'`). rmw_zenoh's default mode is peer; a peer pointed at a robot's router saw 7 of ~240 topics and received 0 messages (the robot's nodes are peers listening on its localhost, and Clearpath's router config has `peers_failover_brokering: false`). As a client, or through the base station's router, everything arrives at full rate.
- **Data stalls are caused by subscribe/unsubscribe, not by data volume.** The robot's local delivery never stalls, a deliberately slow subscriber doesn't stall anything (zenoh drops for it), WiFi was -41 dBm / 866 Mbit/s and the rate limits above didn't change it; but each new subscription from the base station pauses that robot's data ~0.3 s, and 65 topics subscribed or dropped at once pin the robot's `rmw_zenohd` at ~100 % of a core for 2-3 s, 1-5 s gaps at the base station (zenoh 1.8.0 everywhere). So: long-lived subscriptions, RViz with the displays you need, per-robot tools as clients of that robot's router (the web UI does). Two robots through the base station's router (a300_00036 + a simulated j100_0921) ran 10 min without the 2026-10-06 deadlock; the simulated robot's data was unaffected by a300_00036's stalls. **Two real robots through the base station's router do not work** (a300_00036 + a200_0284, 2026-10-07): when a200_0284's router restarted, the base station's router lost its topics ("router declaration with unknown routing context id", "Unable to push non droppable network message"), and restarting the base station's router left one robot or the other without data ("Route data with unknown scope", "LinkState ... unknown node mapping"), with no load at all. Each robot alone through it works, and survives that robot's router restarting. So list at most one real robot in `BASESTATION_ZENOH_CONNECT`; reach the others as clients of their own routers.
- **Cyclone DDS** (tried on a300_00036, then reverted to zenoh): `implementation: rmw_cyclonedds_cpp`, `discovery: simple` (server is Fast DDS only). Cyclone's default participant index allows ~10 ROS processes per host; the robot runs ~30 ("Failed to find a free participant index for domain 0", most nodes down) -- it needs a `CYCLONEDDS_URI` config with `<Discovery><ParticipantIndex>none</ParticipantIndex>` and the WiFi `<NetworkInterface>` (the robot also has `br0` for sensors and the arm), set through robot.yaml `system.bash.env` (Clearpath docs). The base station follows with `BASESTATION_RMW=rmw_cyclonedds_cpp` in `.env` (`basestation.compose.yml`); the sim and other robots stay on zenoh and can't see that robot. This host's ufw drops the robot-initiated UDP: `sudo ufw allow proto udp from 192.168.50.0/24 to any port 7400:7500`.
