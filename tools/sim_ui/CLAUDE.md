# tools/sim_ui

Moved out of the root CLAUDE.md (loads when working under this directory; the root file links here).

**Modes: sim, real robots, or both** (2026-10-06). The header's selector (per browser, `localStorage`; `--mode` sets the default) picks what the page shows: the Simulation and Spawn cards (`.only-sim`), the Real robots card (`.only-real`), and which robots the Robots card lists (`/api/status?mode=`). Every per-robot API takes `{robot, kind}` (`kind` `sim`, the default, or `real`); `resolve()` in `server.py` returns a `SimTarget` (`docker exec <c> bash -c`) or a `RealTarget` (`ssh robot@host "bash -c '<cmd>'"`, after sourcing `/etc/clearpath/setup.bash` and exporting `ROBOT_NAMESPACE`, which a robot's own shell doesn't set; `BatchMode`, a ControlMaster socket under `/tmp/fleet-ui-ssh-<uid>/` so polls reuse one connection; stdin from `/dev/null`, else ssh reads the server's terminal). Commands run inside `bash -c`, so every `pgrep`/`pkill` pattern brackets its first letter (`[r]os2 ...`) or it matches the shell running it.
- **Real robots** are listed in `real_robots.json` (`{"<id>": {"host", "user", "cutter"}}`, edited from the card: Add / update, Remove, the cutter checkbox; host defaults to `cpr-<id with ->.local`, which doesn't resolve for j100_0921 on the lab network, so give an IP). `cutter` gates Cut stem: `bringup_main` advertises `cut_stem` on every robot, so the action's existence says nothing. Per robot: online/offline (an unreachable one is retried in the background every 15 s, so it doesn't stall polls), the deployed commit (`~/colcon_ws/DEPLOYED`) and whether its `colcon_ws/src` equals HEAD's (`git diff <deployed> HEAD -- colcon_ws/src`; a commit compare alone called a300_00036 out of date with 0 files to update), whether the robot's `platform/joint_states` reaches the base station (`ros2 topic list -v` there; the configured `BASESTATION_ZENOH_CONNECT` alone isn't enough: on 2026-10-06 the base station held a TCP link to a300_00036's router, which logged "Could not find corresponding link in routers network" and routed nothing; a Link button adds a missing endpoint and recreates the base station), Dry run / Deploy (`deploy_robot.sh --yes`, after a browser confirm, since its own delete prompt needs a tty) / Pull.
- **Real robot actions**: Restart services = `sudo -n systemctl restart clearpath-robot` (bringup_main runs from `clearpath-platform-extras`; sudo there needs a password, so the job prints the sudoers line to add), Service log = `journalctl -u clearpath-platform-extras`, arm moves planned only and velocity <= 0.3, RViz in the base station container (`namespace:=<id> use_sim_time:=false`). Every real action that moves something asks in the browser first.
- **Stop motion** (per robot) / **Stop all motion** (header, every robot of the mode): SIGINT to the page's `cut_stem` / `arm_goto` clients, then a `CancelGoal` with a zero goal id (= all goals) on `cut_stem`, `move_action`, `execute_trajectory` and the arm's trajectory / gripper controllers, so a goal stops even when its client is gone. Verified in the sim: SIGINT on cut_stem -> grid_cutter "Received request to cancel goal", move_group PREEMPTED; a bare `move_action` cancel mid-move -> PREEMPTED.
- **Name clash**: a running sim robot and an online real robot with the same name share every ROS name, and the base station bridges the sim's router and the robots', so `resolve()` refuses actions on either (stop and read-only calls excepted); both rows show "name clash". Verified with a fake real entry.
- `FLEET_ROOT=<checkout>` makes the server drive another checkout's fleet (`.env`, scripts, `sim/`), e.g. this UI from a git worktree against the main checkout's running sim; `real_robots.json` is still read next to `server.py`.

- **`tools/sim_ui/`** (`server.py` + `index.html`, stdlib only, no pip deps): a local web UI that just runs the same scripts/commands listed above -- Start takes a **View** (`Stream (WebRTC)` / `Headed (local window)`), written to `.env` as `SIM_MODE` (`docker/isaac-entrypoint.sh` runs `runheadless.sh` or the desktop `isaac-sim.sh`; compose passes `DISPLAY`, `XAUTHORITY` and the X11 socket to the sim, harmless when streaming; for headed the server uses its `$DISPLAY` or the first `/tmp/.X11-unix` socket and runs `scripts/x11_auth.sh` first) a **Scene** (`SIM_SCENE` in `.env`, a change recreates the sim; a scene that fails to load shows the sim's traceback under Simulation): a *Choose file...* button (opens a hidden `<input type=file>`, whose own "No file chosen" text would reset after every pick and page reload; the label next to it shows the current/chosen scene) plus a *Default scene* button (ground plane + lights). A browser only hands the page a picked file's *contents*, not its path, and a saved scene's assets are relative to it (`../assets/...`), so the page uploads it (`/api/scene/upload`, base64 JSON, <= 512 MB) and the server uses the file under `sim/scene/` with the same SHA-256 in place, or else copies it into `sim/scene/` (never over a different file: `<stem>_<hash8>.usd`); Start sends the resulting path, validated against `sim/scene/`'s files. `SIM_SCENE=lavender` (the farm) is only set through `.env` now; your Save As of it in `sim/scene/` loads the same world and a **Robot look** (`Full` / `Basic` / `Off`), written to `.env` as `ROBOT_LOOKS` (`sim/scripts/robot_looks.py`; a change recreates the sim like View does, *Reset scene* keeps the running sim's value; added to test the 3-robot RTX driver crash, see the root CLAUDE.md) -- `scripts/fleet.sh scene` (Start: the sim with the scene only, the job waits for it) and `scripts/fleet.sh spawn --poses <json>` (Spawn, after writing `NUM_ROBOTS`/`ROBOT_MODEL_<i>` to `.env`; the form has model + x/y/yaw per slot, *Default poses* from the sim's `state.json`, and a top-down canvas map of the lavender rows, the robots in the scene and the form's poses -- click a robot to select it, click elsewhere to move it; the Spawn button is enabled once the sim reports the scene ready; the model list is the sim's own imported `models`), `scripts/stop_sim.sh`, `fleet_ctl.reset` ("Reset scene": the robot containers are stopped first -- verified: a running `cut_stem` is gone before the sim restarts -- then the running sim stops and plays its timeline, then the containers start again; like Isaac's Stop/Play buttons, ~3.5 s instead of the ~1 min container restart it used to be; robots, arm joints included, go back to their spawn state -- verified by GPS: 0.81 m driven, 2 mm after the reset; `docker restart <robot>` still doesn't reset anything physical), `restart_ros`, and the two helpers `arm_goto`/`arm_joints` (`moveit_sim_bridge`'s, from `~/colcon_ws`; an older sim image's `/usr/local/bin` copy as a fallback). Long actions run as background jobs whose output the page polls. "Record" on an arm move runs `arm_joints --record` alongside it and plots commanded vs. observed per joint -- the same comparison used to diagnose the `joint_2` tracking problems below. Binds 127.0.0.1 by default (`--host 0.0.0.0` exposes docker control to the LAN); POSTs require `Content-Type: application/json` so other websites can't drive it cross-site. Arm moves need `sim_robot_upstart.launch.py` running (MoveIt plan mode needs `move_group`; both modes need `moveit_sim_bridge`); the SRDF's duplicate `zero` state is de-duplicated (first wins). Each robot card also has **Cut stem** / **Stop cutting** buttons (`/api/cutstem/start|stop`): start runs `ros2 action send_goal --feedback /<ns>/cut_stem plant_cutter_msgs/action/CutStem "{start_cutting: true}"` inside the robot as a job (per-patch feedback streams into the Jobs log; it first checks the action exists, i.e. `sim_robot_upstart` is up), stop sends SIGINT to that client, which cancels the goal (the server logs "Received request to cancel goal"); a "cutting" pill shows while a client is running (detected by `pgrep` on the `ros2 action send_goal.*cut_stem` process).

**RViz** row per robot card (`/api/rviz/start`, `view` = `navigation`/`moveit`/`robot`): runs `ros2 launch clearpath_viz view_<view>.launch.py namespace:=$ROBOT_NAMESPACE use_sim_time:=$USE_SIM_TIME` detached in the robot (output in `/tmp/rviz_<view>.log`), after refreshing `/tmp/.docker.xauth` with `scripts/x11_auth.sh`. `clearpath_viz` comes from `colcon_ws/src/clearpath_desktop` and must be built (`scripts/colcon_build.sh --packages-select clearpath_viz`). A button reads "(open)" and is disabled while its launch runs; the launch exits when its window is closed.

**Motion capture** card (`/api/mocap?server=<ip>`, `/api/mocap/assign`): while the page polls (Listen), `MocapMonitor` listens to OptiTrack Motive's NatNet stream on this host (default 192.168.50.80; it registers for unicast and joins the default multicast group, so either transmission type works; stops 30 s after the last poll) with the parser the robots use (`colcon_ws/src/mocap_fake_localizer/scripts/natnet.py`, stdlib only, imported by path), and lists the rigid bodies (tracked, position, yaw, mean marker error) and the rate. Each row's **Robot** dropdown (MTU's real robot ids + running sim robots) writes `mtu32_bringup/config/ref_localization/assignments.yaml` (`/<ns>/natnet_ref_pose: rigid_body`, JSON under a comment header -- valid YAML, and the server needs no YAML library), which `bringup_main.launch.py` loads between `ref_localization.yaml` and the hand-written `<ns>.yaml`; one robot per rigid body, a robot without an entry follows the rigid body named after it ("(by name)"). Real robots get it with `colcon_ws/src`. Tested against a fake NatNet 2.8 server (Motive was offline): rate, tracking, assignment / reassignment, and the file loaded by `natnet_ref_pose`. Against the real Motive 1.79 / NatNet 2.8: the host firewall (ufw, default deny incoming) drops the frame data (from Motive's port 1511, not a reply to anything this host sent) while Motive's replies to NAT_CONNECT / model requests pass, so the card shows Motive and its rigid body names but no frames -- `sudo ufw allow from 192.168.50.80 to any port 1511 proto udp`. A row whose values are from the last frame received shows as *stale*. **Localization** section per robot card (`/api/localization?robot=`, `/api/localization/set`): `ref_localizer/status` read with `ros2 topic echo --once` (a few seconds), `ros2 param set` for source / anchor, `save_anchor` / `reset_anchor` service calls (a `success=False` response fails the job). Jobs returning `False` used to show as done (`False == 0` in the old `ok in (None, True, 0)`); fixed.
