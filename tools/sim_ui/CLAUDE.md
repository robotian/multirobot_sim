# tools/sim_ui

Moved out of the root CLAUDE.md (loads when working under this directory; the root file links here).

- **`tools/sim_ui/`** (`server.py` + `index.html`, stdlib only, no pip deps): a local web UI that just runs the same scripts/commands listed above -- Start takes a **View** (`Stream (WebRTC)` / `Headed (local window)`), written to `.env` as `SIM_MODE` (`docker/isaac-entrypoint.sh` runs `runheadless.sh` or the desktop `isaac-sim.sh`; compose passes `DISPLAY`, `XAUTHORITY` and the X11 socket to the sim, harmless when streaming; for headed the server uses its `$DISPLAY` or the first `/tmp/.X11-unix` socket and runs `scripts/x11_auth.sh` first) a **Scene** (`SIM_SCENE` in `.env`, a change recreates the sim; a scene that fails to load shows the sim's traceback under Simulation): a *Choose file...* button (opens a hidden `<input type=file>`, whose own "No file chosen" text would reset after every pick and page reload; the label next to it shows the current/chosen scene) plus a *Default scene* button (ground plane + lights). A browser only hands the page a picked file's *contents*, not its path, and a saved scene's assets are relative to it (`../assets/...`), so the page uploads it (`/api/scene/upload`, base64 JSON, <= 512 MB) and the server uses the file under `sim/scene/` with the same SHA-256 in place, or else copies it into `sim/scene/` (never over a different file: `<stem>_<hash8>.usd`); Start sends the resulting path, validated against `sim/scene/`'s files. `SIM_SCENE=lavender` (the farm) is only set through `.env` now; your Save As of it in `sim/scene/` loads the same world and a **Robot look** (`Full` / `Basic` / `Off`), written to `.env` as `ROBOT_LOOKS` (`sim/scripts/robot_looks.py`; a change recreates the sim like View does, *Reset scene* keeps the running sim's value; added to test the 3-robot RTX driver crash, see the root CLAUDE.md) -- `scripts/fleet.sh scene` (Start: the sim with the scene only, the job waits for it) and `scripts/fleet.sh spawn --poses <json>` (Spawn, after writing `NUM_ROBOTS`/`ROBOT_MODEL_<i>` to `.env`; the form has model + x/y/yaw per slot, *Default poses* from the sim's `state.json`, and a top-down canvas map of the lavender rows, the robots in the scene and the form's poses -- click a robot to select it, click elsewhere to move it; the Spawn button is enabled once the sim reports the scene ready; the model list is the sim's own imported `models`), `scripts/stop_sim.sh`, `fleet_ctl.reset` ("Reset scene": the robot containers are stopped first -- verified: a running `cut_stem` is gone before the sim restarts -- then the running sim stops and plays its timeline, then the containers start again; like Isaac's Stop/Play buttons, ~3.5 s instead of the ~1 min container restart it used to be; robots, arm joints included, go back to their spawn state -- verified by GPS: 0.81 m driven, 2 mm after the reset; `docker restart <robot>` still doesn't reset anything physical), `restart_ros`, and the two in-container helpers `arm_goto`/`arm_joints` (`robot/bin/`). Long actions run as background jobs whose output the page polls. "Record" on an arm move runs `arm_joints --record` alongside it and plots commanded vs. observed per joint -- the same comparison used to diagnose the `joint_2` tracking problems below. Binds 127.0.0.1 by default (`--host 0.0.0.0` exposes docker control to the LAN); POSTs require `Content-Type: application/json` so other websites can't drive it cross-site. Arm moves need `sim_robot_upstart.launch.py` running (MoveIt plan mode needs `move_group`; both modes need `moveit_sim_bridge`); the SRDF's duplicate `zero` state is de-duplicated (first wins). Each robot card also has **Cut stem** / **Stop cutting** buttons (`/api/cutstem/start|stop`): start runs `ros2 action send_goal --feedback /<ns>/cut_stem plant_cutter_msgs/action/CutStem "{start_cutting: true}"` inside the robot as a job (per-patch feedback streams into the Jobs log; it first checks the action exists, i.e. `sim_robot_upstart` is up), stop sends SIGINT to that client, which cancels the goal (the server logs "Received request to cancel goal"); a "cutting" pill shows while a client is running (detected by `pgrep` on the `ros2 action send_goal.*cut_stem` process).

**RViz** row per robot card (`/api/rviz/start`, `view` = `navigation`/`moveit`/`robot`): runs `ros2 launch clearpath_viz view_<view>.launch.py namespace:=$ROBOT_NAMESPACE use_sim_time:=$USE_SIM_TIME` detached in the robot (output in `/tmp/rviz_<view>.log`), after refreshing `/tmp/.docker.xauth` with `scripts/x11_auth.sh`. `clearpath_viz` comes from `colcon_ws/src/clearpath_desktop` and must be built (`scripts/colcon_build.sh --packages-select clearpath_viz`). A button reads "(open)" and is disabled while its launch runs; the launch exits when its window is closed.

**Motion capture** card (`/api/mocap?server=<ip>`, `/api/mocap/assign`): while the page polls (Listen), `MocapMonitor` listens to OptiTrack Motive's NatNet stream on this host (default 192.168.50.80; it registers for unicast and joins the default multicast group, so either transmission type works; stops 30 s after the last poll) with the parser the robots use (`colcon_ws/src/mocap_fake_localizer/scripts/natnet.py`, stdlib only, imported by path), and lists the rigid bodies (tracked, position, yaw, mean marker error) and the rate. Each row's **Robot** dropdown (MTU's real robot ids + running sim robots) writes `mtu32_bringup/config/ref_localization/assignments.yaml` (`/<ns>/natnet_ref_pose: rigid_body`, JSON under a comment header -- valid YAML, and the server needs no YAML library), which `bringup_main.launch.py` loads between `ref_localization.yaml` and the hand-written `<ns>.yaml`; one robot per rigid body, a robot without an entry follows the rigid body named after it ("(by name)"). Real robots get it with `colcon_ws/src`. Tested against a fake NatNet 2.8 server (Motive was offline): rate, tracking, assignment / reassignment, and the file loaded by `natnet_ref_pose`. Against the real Motive 1.79 / NatNet 2.8: the host firewall (ufw, default deny incoming) drops the frame data (from Motive's port 1511, not a reply to anything this host sent) while Motive's replies to NAT_CONNECT / model requests pass, so the card shows Motive and its rigid body names but no frames -- `sudo ufw allow from 192.168.50.80 to any port 1511 proto udp`. A row whose values are from the last frame received shows as *stale*. **Localization** section per robot card (`/api/localization?robot=`, `/api/localization/set`): `ref_localizer/status` read with `ros2 topic echo --once` (a few seconds), `ros2 param set` for source / anchor, `save_anchor` / `reset_anchor` service calls (a `success=False` response fails the job). Jobs returning `False` used to show as done (`False == 0` in the old `ok in (None, True, 0)`); fixed.
