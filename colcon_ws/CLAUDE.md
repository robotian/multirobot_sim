- **`sim_robot_upstart.launch.py`** (in `colcon_ws/src/mtu32_husky/mtu32_bringup/launch/`, MTU's own private package — the user's chosen main launch file for driving a real robot against this sim, now including `bringup_main.launch.py`): launches `bringup_main.launch.py`'s own node set (it used to also start `robot_localization`'s `ekf_node` with `publish_tf` forced `False`; the EKF is now the container's own `ekf` boot service, see below): `laser_filters`' `scan_to_scan_filter_chain`, `depthimage_to_laserscan`, `apriltag_ros`'s `apriltag_node`, `docking_utils`' `tf2_pose_node`, `stow_arm_cpp`'s `pcl_filter`/`grid_cutter` nodes, `pruner_action_server`, `kinova_game_pad`'s gamepad node, and (after a `moveit_delay` `TimerAction`) `moveit.launch.py`'s `move_group`+`moveit_servo`. None of these are generic Clearpath output — they're MTU's own real bringup, vendored as source in `robot_data/j100_0921/colcon_ws/src/` (that robot's own real, working workspace) and copied into the shared `colcon_ws/src/` (mocap_fake_localizer, docking_utils, stow_arm_cpp, pruner_action_server, kinova_game_pad, laser_filters, depthimage_to_laserscan, apriltag_ros, plant_cutter_msgs, serial_interfaces — copied verbatim rather than substituted with apt equivalents, to stay version/config-consistent with the launch/config files written against them) plus `pcl_ros`/`moveit_ros_move_group`/`moveit_servo`/`apriltag`/`apriltag-msgs`/`camera-ros`/`python3-serial` added to `robot/Dockerfile`'s apt list (genuine framework/library dependencies, not vendored in `robot_data` since the real robot installs those from apt too). Two real bugs found and fixed in `sim_robot_upstart.launch.py` itself (the user's own file, already using the same `publish_tf: False` override independently arrived at earlier this session) while getting it running: (1) `nav2_common` (imported for `RewrittenYaml`, unused in this specific file but genuinely used across most of `mtu32_bringup`'s other launch files) wasn't installed — added `ros-jazzy-nav2-common`; (2) the `ekf_node`'s `Node()` action never set `name='ekf_node'`, so it ran under `robot_localization`'s own default name `ekf_filter_node` instead — silently mismatching the generated `localization.yaml`'s own node-name-keyed structure (`j100_0921: ekf_node: ...`), so none of the real tuned values (frequency, `odom0`) ever actually applied; it ran, but fused nothing. Verified live end-to-end (a full 20+s run, not just a launch-and-check): all expected nodes stay up (no deaths), `move_group`/`servo_node` both load the real robot model and initialize successfully (servo's own twist-mode activation call returns `success=True`), `drive_test.py` still passes afterward. **Known, accepted-as-out-of-scope remaining warnings, not chased further**: the `arm_0_gripper` planning group logs `'is not a chain'` and gets no KDL kinematics solver — expected and harmless, a parallel-jaw gripper group doesn't need IK; `move_group` logs "No 3D sensor plugin(s) defined for octomap updates" — expected, no 3D perception source is configured for the arm's environment awareness. `tf2_pose_node`'s `jackal_charger_april` TF lookup failures are also expected — that frame only exists once an AprilTag dock target is actually visible in the camera, which nothing in the current scene provides.

- **`moveit_sim_bridge`** (new package, `colcon_ws/src/moveit_sim_bridge/`, launched as another `Node()` in `sim_robot_upstart.launch.py`'s own `load_nodes`): closes the gap the above verification originally missed — `move_group`/`grid_cutter_action_server` initialized fine, but the real `cut_stem` action (`ros2 action send_goal /<ns>/cut_stem plant_cutter_msgs/action/CutStem "{start_cutting: true}"`) accepted goals yet the arm never actually moved. Root cause, confirmed live: `move_group`'s own `moveit_simple_controller_manager` plugin is a real, permanent **client** of `.../manipulators/arm_0_joint_trajectory_controller/follow_joint_trajectory` (`control_msgs/action/FollowJointTrajectory`), expecting a real `ros2_control`-based controller on the other end — this project's arm has none (Isaac's own OmniGraph drives it directly via `arm_0/joint_command`, see `configure_arm_drives`/the "Arm + gripper" OmniGraph section in `sim/scripts/setup_scene.py`), so `ros2 action info` showed 0 servers and every `execute()` call failed instantly with `CONTROL_FAILED` (MoveIt error code -4). Confirmed with the user before building new infrastructure (an explicit reversal of the earlier "exclude ros2_control for now" decision, since this specific goal genuinely needs *some* execution path). `moveit_sim_bridge` is a small rclpy node providing exactly that execution path — not a general ros2_control hardware interface plugin — with three pieces: (1) a `FollowJointTrajectory` action server at that exact name, playing a planned trajectory's waypoints back at their own `time_from_start` pacing as `sensor_msgs/JointState` position commands published to `arm_0/joint_command` (time-based, not feedback-convergence-based — a disclosed sim-bridge simplification, since `IsaacArticulationController`'s own already-tuned position servo is what actually gets the arm there); (2) a `GripperCommand` action server at `.../arm_0_gripper_controller/gripper_cmd` for the Kinova 2F Lite's 4 finger joints — of which only `arm_0_gripper_right_finger_bottom_joint` is actually independently actuated in the real URDF, the other 3 being `<mimic>` joints of it (confirmed by reading `/etc/clearpath/robot.urdf` directly, not assumed from the SRDF group name) with their own real multipliers, two of them *negative* (`-0.676`, for both finger tip joints); overridable via the `gripper_joint_names`/`gripper_joint_multipliers` parameters for a different gripper; (3) a plain topic subscriber on `.../arm_0_joint_trajectory_controller/joint_trajectory` — found necessary only after the action-server fix alone still left `grid_cutter_action_server`'s own *servo*-based fine-approach phase timing out, because `moveit_servo`'s `command_out_type: trajectory_msgs/JointTrajectory` (see `mtu32_bringup`'s `servo_config.yaml`) streams single-point trajectories directly to a plain topic, never through the action at all. Verified live after both fixes: the arm's own `platform/joint_states` genuinely change on a `cut_stem` goal (`arm_0_joint_1`/`_2` moved from ~0 to -0.51/-1.37 rad), `grid_cutter_action_server` logs real `Execute request success!`/`Reached '...'` for its move_group-planned poses. **A fourth real bug found next, once the arm itself worked**: the gripper opened on cue but never actually closed during the real `cut_stem` sequence, even though its own `GripperCommand` goal reported success — confirmed live, the hard way: an isolated, direct `GripperCommand` goal (nothing else running) genuinely closed the gripper and it *stayed* closed; but the instant any subsequent arm-only command arrived (a `moveit_servo` stream point, or the next trajectory goal) the gripper silently reopened. Root cause: `arm_0/joint_command`'s subscriber (`ROS2SubscribeJointState`/`IsaacArticulationController`) only ever remembers the *last full message's* own name/position arrays — this bridge was publishing separate arm-only and gripper-only messages, so any arm-only message wholesale replaced the commanded set and dropped the gripper's just-closed target the instant it arrived (not a race, a guarantee, since `grid_cutter_action_server`'s own `try_prune_once` always calls another arm servo move immediately after closing the gripper). Fixed by having the bridge keep its own last-known position for *every* joint it's ever been told about and publish all of them together on every update, so a gripper command can never again be silently overwritten by an unrelated arm command or vice versa. **One more thing found and fixed along the way, unrelated to the bridge's own code**: repeated testing during this specific investigation had left the arm/gripper in a physically corrupted state (gripper joints reading wildly out of range, e.g. 2.5 rad, and an arm joint stuck ~2.3 rad off target and not converging even when correctly commanded back to 0) — a genuine physical side effect of the pre-fix bug (a joint dropped from the commanded array while its position servo held a stale target can end up essentially undriven), not something a ROS-side container restart can clear since Isaac Sim (a separate container) owns that physics state; only restarting `a300-isaac-sim` itself actually reset it. Verified live after all of this, on a freshly-reset arm: the gripper genuinely closes and *holds* through subsequent arm motion (confirmed via `platform/joint_states`, not just the action's own reported result), matching `grid_cutter_action_server`'s own real open→approach→close→(pruner attempt)→reopen-and-retry cycle. **A fifth bug, reported directly by the user as "the gripper motion is reversed — it closes with opening motion command, vice versa"**: the gripper-close fix above made the gripper hold correctly, but its direction was wrong for at least some joints. Root cause, found by reading the actual URDF's own `<mimic>` tags rather than guessing: this bridge was sending `GripperCommand`'s single `position` value identically to all 4 joint names, completely ignoring that 3 of them are mimics with their own multiplier (`1.0`, `1.0`, and — for both finger tip joints — `-0.676`, an inverted sign relative to the one real driven joint). Sending the same raw value to a joint whose real multiplier is negative drives it in the wrong rotational sense entirely, which is exactly what "reversed" looks like from outside. Fixed by treating `position` as `arm_0_gripper_right_finger_bottom_joint`'s own raw value and deriving the other 3 from their real multipliers instead of copying it verbatim. Verified live: closing (`position: 0.9`) now moves both bottom joints positive (`~0.75`, limited by contact/settle time short of the full `0.9` target) and both tip joints negative (`-0.5`, correctly clamped at that joint's own URDF lower limit of `-0.50`) — a consistent, physically sensible closing motion instead of a mixed one; opening (`position: 0.0`) returns all 4 to ~0. Since the fix, the action's own end-to-end "patch" also failed for a completely different, then-still-open reason: each patch's own next step called `pruner_server` (`Received goal to send integer: 42`) which failed with `Cannot send data. Serial port is not open` — no `/dev/ttyOpenCR` device existed in the container at all. See `pruner_stub` below for how that gap was closed too. **A sixth bug, reported directly by the user after the pruner fix, comparing against real-robot behavior they'd tested themselves**: "the arm moves too fast compare to the real robot... and it is overshooting at the goal position." Root cause: `_execute_trajectory` (piece (1) above) was publishing exactly one `JointState` per trajectory waypoint, at that waypoint's own `time_from_start` — a real `JointTrajectoryController` continuously *interpolates* between a planned trajectory's (often sparse) waypoints, so a real robot's commanded position ramps smoothly; this bridge was instead handing `IsaacArticulationController`'s PD position servo (`configure_arm_drives`' own `STIFFNESS`/`DAMPING`, already documented there as untuned against a real robot) a sequence of large instantaneous target jumps, which it then tried to close as fast as its own gains allowed — fast, and prone to overshoot on a step input, independent of how slowly the trajectory itself was actually paced. Fixed by linearly interpolating between consecutive waypoints at a fixed `INTERP_PERIOD_S` (50Hz, roughly a real JTC's own control-loop cadence) instead of jumping straight to each one — removes the step inputs without needing to retune the PD gains themselves. Verified live with a controlled, timestamp-correlated single-joint test (not just eyeballing it): a 2-point trajectory (0.0 → 1.0 rad over a planned 4s) produced a smooth ramp (0.09 rad at +0.5s, ~1.0 rad by +5s) settling at `1.0001` — no measurable overshoot, versus jumping straight to the far target instantly beforehand. Re-verified the real `cut_stem` sequence and `drive_test.py` still work after the change.

- **`arm_0_joint_2`: the root cause of its tracking problems was its torque limit, not its gain** (`ARM_JOINT_2_MAX_FORCE = 40.0` in `configure_arm_drives` — since generalised to `ARM_EFFORT_SCALE = 3.0` on every `arm_0_joint_N`, see the a200_0284 paragraph; the importer had copied the URDF effort limit, 14 N·m, into the drive's `maxForce`, and `configure_arm_drives` never touched it). Found with the web UI's recording plus `platform/joint_states`' effort field: joint_2 sat at 13.9995 N·m (saturated) near cut_init, dropped from −0.65 to −2.1 rad mid-move, and could only move *with* gravity — the same one-directional block as the patch-2 stall described next. With 40 N·m: every `zero`↔`cut_init` move tracks within ~0.06 rad, and a full `cut_stem` ran 9+ patches with no stall (joint_2 peak 24 N·m, above 14 N·m for 27% of the run). Gains from 1e4/1e3 to 1e7/1e6 all need the same torque, so the special joint_2 gain is no longer what matters (kept, harmless). **Open, accepted as a disclosed workaround**: the sim needs ~1.5× (holding) to ~2× (moving) the torque that static gravity from the URDF masses predicts (masses match the imported USD; FK check matches at `zero`, 0.92 vs 0.94 N·m measured), while the real arm works within 14 N·m. Self-collision and joint friction are ruled out; chassis pitch/rocking is untested.

**`cut_stem` on `a200_0284` (Gen3 *7-DOF* + Robotiq 2F-85) with the *same* `colcon_ws/src` as the Jackal — what it took (result: "Cut 14/14 patches", SUCCEEDED; `a300_00036`/Lite re-verified 20/20 afterwards):** the shared packages are tuned for the Jackal's Gen3 Lite, so differences live in **per-robot overrides**, not forks. (1) `stow_arm_cpp/launch/grid_cutter.launch.py` now also loads an optional `config/robots/<namespace>.yaml` after the shared `grid_cutter_params.yaml`; `config/robots/a200_0284.yaml` holds what differs (7-value IK seed found by scoring compute_ik solutions over the whole zone incl. the approach points; cutting zone x 0.50–0.62 because the Lite's 0.20–0.38 forces a contorted pose; Robotiq `gripper_close` 0.8; ground-plane box lowered to this arm's 0.411 m base height; `moveit_vel_scale`/`acc_scale` 0.4 because the sim's wrist joints only slew ~0.5–0.8 rad/s against the URDF's 1.22; joint-space `drop_joint_positions` because its robot.yaml defines no `drop` pose — **assumed to be above its `basket` box, please replace with a real pose**). The cutter C++ gained `drop_joint_positions` (empty = named `drop_pose`) and `drop_lower_distance` (default 0.1 = old behaviour), now a **common** parameter: `grid_cutter_params.yaml` sets 0.1 for every robot and `a200_0284.yaml` no longer overrides it (the "14/14" run above was made with a per-robot `0`; the servo lowering 10 cm from its drop pose has **not been re-verified** on a200_0284 -- if it stops at "singularity", set `drop_lower_distance: 0` in `config/robots/a200_0284.yaml`). (2) `robot/bin/robot_state` now also writes the *pruned* description over `/etc/clearpath/robot.urdf.xacro` when it pruned something (this robot's `links.box` `basket` has `parent: arm_base_link`, which doesn't exist, so `moveit.launch.py`'s raw xacro made move_group/servo/cutter die), and gives the arm's `continuous` joints ±3.12 limits (`scripts/flatten_urdf.py`'s `limit_continuous_arm_joints` does the same for the sim's URDF): MoveIt plans across ±π, the simulated joint ended at e.g. 4.995 rad, and MoveIt then rejects the state (`START_STATE_INVALID`, verified 4.995 → invalid, 3.0 → success). (3) `moveit_sim_bridge`: the gripper joints/multipliers/offsets are now read from the robot's own `robot_description` (fallback: the old Kinova 2F Lite values; note the Lite's finger tips have a mimic *offset* of +0.149 that the old hardcoded values ignored), it logs each trajectory, and it now **waits for the arm to settle** (`settle_tolerance` 0.03 rad, `settle_timeout` 10 s) before reporting a trajectory done. (4) `setup_scene.py`: `ARM_EFFORT_SCALE = 3.0` replaces the fixed joint_2 40 N·m (each `arm_0_joint_N` gets 3× its own URDF effort: Lite joint_2 14→42, Gen3 39→117); the Gen3's joint 2 saturated at the old 40 and the arm collapsed. (5) **The Robotiq's `<mimic>` followers are `continuous` with no limits, which the physics engine rejects ("NewtonMimicAPI follower joint … requires a finite limit", ending in a hard sim crash on some starts); `flatten_urdf.py` (`limit_continuous_mimic_followers`) gives them limits mapped from the mimic relation. Even then the importer's `NewtonMimicAPI` constraints had wrong coefficients (an inner knuckle moved 8× its driver; a joint commanded alone dragged all the others; closing past ~0.3 rad threw the fingers >1 rad past their limits and spun the wrist to −6.6 rad — identical numbers whatever the gains, force cap, self-collision setting, so those were red herrings), so `MODEL_PARAMS["a200_0284"]["drop_mimic_constraints"]` removes the whole `NewtonMimicAPI` schema at runtime (clearing just the target relationship did nothing); the bridge already commands every gripper joint. Debugging aids worth reusing: the `arm_joints --record` UI plots, `platform/joint_states` efforts (a 672 N·m spike = the arm hit something), and `ros2 topic pub` on `arm_0/joint_command` for single-joint tests — but only on a *fresh* sim: after a run goes chaotic (joints tens of rad past their limits) everything measured afterwards is meaningless, reset first. **Sim start is flaky**: ~3 of ~35 starts today either hung in Kit at ~35 s (log silent, no `[fleet]` line, CPU 57%) or segfaulted (exit 139) a second after "simulation running"; a second `docker restart a300-isaac-sim` cleared it every time.

**Gripper follow-up (user: RViz gripper plan OK, execution fails):** (a) `moveit_sim_bridge`'s GripperCommand slept a fixed 1.0 s; MoveIt allows trajectory duration × 1.2 + 0.5 s, i.e. 0.5 s for a near-zero plan (RViz "close" while already closed) → `TIMED_OUT`. It now finishes when the driven joint is within `gripper_tolerance` (0.02) of the target, when it stops moving (stall, e.g. holding a stem), or after `gripper_timeout` (3 s). (b) **Mimic constraints are now removed on every arm (`configure_arm_drives(drop_mimic_constraints=True)` default), not just a200_0284**: on the Kinova 2F Lite the importer's constraints (coefficients look right: coef0 0.149, coef1 −0.676) still fought the per-joint drives — commanding only the driven joint moved it 0.04 rad for any target, "close" stalled at 0.689 instead of 0.9, and "open" parked the driven joint at −0.204 (outside its −0.1 limit) once the bridge started sending the URDF's +0.149 tip offset. Without constraints: close 0.906, open ~0, arm untouched. Verified: j100_0921 20/20 with all 60 gripper moves "reached", a200_0284 gripper open/close through move_group at scaling 0.5 and 1.0. **Connecting the WebRTC streaming client stalls the sim for a few seconds** (Kit creates a viewport: "can't find hydra engine 'rtx'", GLFW plugin start-up), enough to make MoveIt fail a move ("couldn't receive full current joint state within 1s") — one j100_0921 run aborted at patch 9 that way; don't connect mid-run.

**Tool frame for `cut_stem` (`tool_link`):** the Gen3 Lite + 2F Lite and the Gen3 + Robotiq 2F-85 put the fingers at different places relative to `arm_0_end_effector_link`, so `grid_cutter_action_server` now works in a *tool frame*: params `tool_link` (default `tool_link`), `tool_xyz`, `tool_rpy` (pose of the tool in `ee_link`, default identity = old behaviour) and `publish_tool_tf` (default true: the node publishes the static TF `arm_0_end_effector_link -> tool_link` into the robot's `tf_static`). Every patch/approach/drop position and `grasp_orientation` is a pose of `tool_link`: the node derives the end-effector pose it hands to MoveIt IK (`base_T_ee = base_T_tool * ee_T_tool^-1`, also in the reachable-circle search), and the servo feedback (`get_ee_position`) looks up `base -> tool_link`. `moveit_servo` needs no change: twists are linear-only, so the tool point moves like the ee origin. Set the offset per robot in `config/robots/<namespace>.yaml`; **defaults are zero, so nothing changes until you do, and the zone/IK seed/drop pose tuned for the ee point (e.g. a200_0284's) must be re-checked after setting an offset.** Measure with `tf2_echo arm_0_end_effector_link <fingertip link>` (Robotiq open: fingertip link origins at x=+-0.068, z=0.098). Verified on a200_0284 with `tool_xyz: [0,0,0.098]`: `tool_link` = `ee` + 0.098 m along the ee z axis, and the first approach was reached with the *tool* at the requested position; the offset was then reverted (not committed).

**Nav2 and outdoor (dual-GPS) localization** (sim twins of the real launch files, in `mtu32_bringup/launch/`; build with `scripts/colcon_build.sh`): `sim_nav2.launch.py` runs the real `navigation_launch.py` with `config/<platform>/nav2.yaml`, patched for the sim (`platform/odom`, no static layer + fixed 100 m global costmap, a `laser_filters` box self-filter -- the simulated lidar sees the robot's own body, which made the collision monitor refuse to move -- and a 30 s progress-checker allowance); by default map->odom is a static identity. The real outdoor flow is `swift_nav_dual.launch.py` then `bringup_nav2_mapping_j100.launch.py`; in the sim it is `sim_swift_nav_dual.launch.py` then `sim_nav2.launch.py gps:=true` (no static map->odom, `nav2_mapping.yaml` when the platform has one). `sim_swift_nav_dual` replaces the two `sbp-to-ros` Duro drivers (they need `libsbp`, not packaged for Ubuntu): the reference fix is the sim's own `sensors/gps_<ref>/fix`, and `duro_sim`'s `baseline_node` (as `att_duro_node`) publishes the fixed-RTK moving baseline (attitude minus reference antenna, NED) from the two fixes; then the real `dual_duro_heading` heading filter, `navsat_transform` and `ekf_global_node` run with `config/<platform>/dual_duro_heading.yaml` (j100's if missing). Antennas come from robot.yaml order -- first = attitude (left), second = reference (right): a200/a300 `gps_0`/`gps_1`, Jackals `gps_1`/`gps_2` -- which is the right->left baseline the heading filter's yaw formula assumes. The datum is overridden to the sim's GPS origin (`GPS_READ_SCRIPT`'s `_ORIGIN_LAT/LON`), so the map frame is the Isaac world frame. `colcon_ws/src/swiftnav_ros2_driver` is a message-only stand-in (the real `Baseline.msg`, verbatim) and `colcon_ws/src/dual_duro_heading` is vendored from `robot_data/j100_0921` with one change: its hardcoded heading frame `gps_2_link` (which a200/a300 don't have) is now a `frame_id` parameter, same default. Verified on a200_0284: `odometry/global` within 3 cm / 1.4 deg of ground truth while driving (fixes are exact, covariance 'unknown'). `gps:=true` Nav2 end to end not yet run.
