# Real robots (robot_data/<id>/robot.yaml) — per-robot notes

A new `robot_data/<id>/` robot (or a changed robot.yaml) needs only `scripts/gen_urdf.sh`, then `docker restart a300-isaac-sim`: the sim derives its parameters at start (drive from the platform + the yaml's `platform_velocity_controller`, sensors/arm from the yaml + flattened URDF, IMU body from `merged_links.json`, chassis_link = the imported articulation root, read at spawn) and logs them as `[fleet] params <id>: ...` — check that line, then `drive_test.py`. Hand tuning goes in `robots.<id>` of `sim/config/model_params.yaml`; never in `setup_scene.py`. The per-robot notes below predate this and speak of hand-written `MODEL_PARAMS` entries; their findings (which link the IMU lands in, why chassis_link moved) are what the derivation now reproduces (verified for all 11 models). `a300_00037` = `a300_00036` with a UR10e + Robotiq 2F-85 (joints `arm_0_shoulder_pan_joint`..`wrist_3_joint`; `configure_arm_drives` matches `arm_0`, they keep their URDF effort limits); spawned, drove, sensors and arm commands verified 2026-10-03, MoveIt/cut_stem not yet. Pipeline details: `scripts/CLAUDE.md`; sim side: `sim/CLAUDE.md`.

**Real robots** (`j100_0921`/`j100_0936`, MTU's own physical Jackals): `j100_0921` generates directly from its own real `robot_data/j100_0921/robot.yaml`, unmodified — see "Real robot.yaml, used directly" below. `j100_0936` (whose own `robot_data` folder isn't currently available) still goes through `robot/config/robot.j100_0936.yaml.tmpl`, built from that robot's own real `robot_data/j100_0936/robot.yaml` (not a generic Clearpath catalog sample) the same way `j100_0921` used to, usable anywhere the 4 model codes above are (`ROBOT_MODEL_<i>` in `.env`, `MODEL_ASSETS`/`MODEL_PARAMS` in `setup_scene.py`, `scripts/gen_urdf.sh`'s `MODELS` list). Both carry each robot's actual sensor/arm loadout — a Stereolabs ZED2i stereo camera, a Microstrain IMU, dual SwiftNav Duro GPS, a Kinova Gen3 Lite arm + 2F Lite gripper, and (0936 only) a SICK LMS1xx 2D lidar — all fully simulated (real ROS2 data / real command handling), not just present as inert geometry. For `j100_0936`, `platform.extras` (the real robot.yaml's own custom `mtu32_description`/`mtu32_bringup` xacro + launch + EKF/velocity-controller overrides — MTU's own private lab packages) is dropped from the template entirely; `generate_description` succeeds cleanly without it (confirmed live), and the numeric calibration values inside it (real wheel-radius/separation multipliers, speed limits) are kept as data in `MODEL_PARAMS` instead. Two real bugs found and fixed while wiring this up originally, both in the templates themselves, not the generator (still apply to `j100_0936`'s template): (1) the real robot.yaml's `sensors.imu[0]`/`links.frame.top_shelf` both reference `parent: top_mount_link`, but nothing in the *stripped* config defines that link — only the dropped `mtu32_description` xacro did — so the template adds a substitute `links.frame` entry aliasing it to `default_mount` (Jackal's standard top-of-chassis mount point); (2) `clearpath_config`'s own hostname validator rejects underscores outright, and a real robot id like `j100_0921` (needed as `ROBOT_MODEL`) fails it two different ways — `docker-compose.yml`'s per-slot `hostname:` (the container's real OS hostname, which `clearpath_config` validates as its own default *before* even reading `robot.yaml`) is `${ROBOT_HOSTNAME_<i>:-cpr-slot-000<i>}`, where `ROBOT_HOSTNAME_<i>` (computed and kept in `.env` by `scripts/fleet.sh`, same mechanism as `ROBOT_SUFFIX_<i>` below, since compose's own interpolation can't turn underscores into hyphens) is `cpr-<model>-<serial>` with `_`→`-` (e.g. `cpr-j100-0921`, `cpr-a300-0000`) — valid by the same rule, but readable instead of a generic `cpr-slot-<i>` fallback — and each real-robot template explicitly sets `system.localhost` to the robot's own correctly-hyphenated serial (`j100_0921` → `j100-0921`) since that's what actually matters for Clearpath tooling. **ROS namespace is the robot's own id directly, no slot suffix** (`j100_0921`, not `j100_0921_0000`) — it's one specific physical robot with one fixed real identity, not a generic model needing a slot index to stay unique. `sim/scripts/setup_scene.py`'s `robot_namespace()` and `robot/entrypoint.sh`'s `ROBOT_NAMESPACE` both special-case this the same way (real robot id contains `_` → use it directly; generic model → `<model>_%04d` as before) since `docker-compose.yml` can't compute it conditionally (no string find/replace in its interpolation syntax, confirmed by testing one directly). The *docker container name* (`docker ps`/`docker exec <name>`) is fixed the same way: `docker-compose.yml`'s `container_name:` is `${ROBOT_MODEL_<i>:-a300}${ROBOT_SUFFIX_<i>-_%04d}` for every slot -- `ROBOT_SUFFIX_<i>` defaults to the usual `_%04d` (unset) but can be overridden to an *empty string* (not merely unset -- `${VAR-default}` without a colon treats those two differently, confirmed by testing directly), which `scripts/fleet.sh` does automatically, writing `ROBOT_SUFFIX_<i>=` into `.env` whenever `ROBOT_MODEL_<i>` contains `_` (and removing it again if that slot's model later changes back to a generic one) -- `docker-compose.yml` itself still can't make this decision (same "no way to inspect a variable's content" limitation as everywhere else this comes up), so it's computed in bash and handed to compose as a plain value instead. Run `scripts/fleet.sh`, not `docker compose up -d` directly, after changing a slot's model for the container name to update. Getting the corrected namespace into `docker exec` shells (`bin/teleop`/`camera_view`/`bin/rviz`, which just read `$ROBOT_NAMESPACE`) needed one more piece: `entrypoint.sh` writes the override to `/etc/robot_ns_env.sh` (freshly overwritten, not appended, so repeated container restarts never accumulate duplicate lines), which `/etc/ros_env.sh` (already sourced by every shell via `BASH_ENV`/`bashrc`) now also sources — compose's own `environment:` block provides the *stale*, slot-suffixed value to fresh `docker exec` sessions otherwise, since that's container-level config `entrypoint.sh`'s own process can't override for sessions it didn't spawn. `sim/scripts/setup_scene.py` needs three more things beyond the generic per-model pipeline: `add_camera`'s `optical_link` parameter (the ZED2i's own xacro already emits a correctly-oriented ROS optical frame, unlike the D435i models' hand-built one), a `configure_arm_drives` pass giving the arm/gripper joints real position-servo stiffness (`IMPORT_SETTINGS`' global `override_joint_stiffness=0.0` is correct for the wheels' pure velocity drive but leaves *every* joint including the arm unable to hold a commanded position at all — confirmed live: a position command barely moved it before this fix), and per-sensor OmniGraph/script-node additions in `build_ros_graph` (IMU/GPS, see their own code comments — both needed a `ScriptNode`, e.g. GPS ended up bypassing `isaacsim.ros2.bridge.ROS2Publisher`, the generic any-message publisher, entirely in favour of a plain `rclpy` publisher created directly in the script, after confirming live that a *connection* into one of that node's dynamically-created inputs silently never propagates a value even though a literal `SET_VALUES` on the same kind of attribute works fine). `j100_0936`'s 2D lidar (SICK LMS1xx) is not yet wired up (its `robot_data` folder isn't currently available to derive the real link name from), but 2D lidar itself is no longer blocked — see the "2D lidar, unblocked" paragraph below for the real, working mechanism (already live on `a200_0333`'s Hokuyo UST); RTX Lidar remains broken in this install, but is no longer the only path. Small in-place rotation commands from a standstill are also weak for these two robots specifically (same static-friction-from-rest phenomenon as Ridgeback, worse here from the arm/sensors' added rotational inertia, further limited by these two robots' own real, deliberately-honoured `max_angular=1.0` cap) — a larger command or one combined with translation works much better; a stuck-in-place robot from repeated small-rotation test attempts turned out to be accumulated test state, not a worsening bug (a `--force-recreate` and fresh test resolved it, matching this project's own established "rule out the mundane explanation first" lesson).

**Real robot.yaml, used directly (`j100_0921`):** once `mtu32_description`/`mtu32_bringup` (MTU's private lab packages `platform.extras` needs) were colcon-built and available, the stripped-template workaround for `j100_0921` was retired in favour of using `robot_data/j100_0921/robot.yaml` completely unmodified, both for host-side URDF generation and the running container's own `/etc/clearpath/robot.yaml` — no `__NS__`/`__SERIAL__`/etc. placeholder substitution at all, since the file's own baked-in `namespace: j100_0921`, `domain_id: 0`, `middleware.implementation: rmw_fastrtps_cpp` and `workspaces: [/home/robot/colcon_ws/install/setup.bash]` already match this project's conventions exactly (confirmed by inspection before relying on it). It also doesn't set `system.localhost`, so `clearpath_config`'s own default (the container's real OS hostname, `ROBOT_HOSTNAME_<i>` = `cpr-j100-0921`) is used — already valid *and* equal to this robot's own `system.hosts[0].hostname`, so no further hostname work was needed. `robot/entrypoint.sh` and `scripts/gen_urdf.sh` each gained the same branch: if a model id contains `_` and `/robot_data/<id>/robot.yaml` exists (bind-mounted read-only from the repo root into every robot container, and into `gen_urdf.sh`'s own throwaway container), `cp` it straight to the destination instead of rendering a `.tmpl`; otherwise the existing template path is unchanged (still used for `j100_0936` and the 4 generic models). `scripts/gen_urdf.sh` also colcon-builds `mtu32_description` (in its throwaway container, from `colcon_ws/src/mtu32_husky/mtu32_description`, the runtime source the robots use) and sources it before calling `generate_description`. It used to build a separate copy in `sim/colcon_ws`, which went stale: a300_00036 kept the old sensor arch, e-stop and button in the sim while Foxglove showed `sensor_arch_v2` and the D405 `camera_1` (fixed 2026-10-03). Two things this actually fixed, not just avoided: `top_mount_link` is now genuinely defined by `mtu32_description`'s own xacro (real mesh + collision, parented on `default_mount`), so the old substitute `links.frame` alias (`top_mount` → `default_mount`) is gone entirely — there's no more fake link to alias; and the new xacro also unconditionally adds a second camera body, `camera_1` (a RealSense D405 on `arm_0_end_effector_link`) — inert geometry only, since `sensors.camera`'s `intel_realsense` entry is still commented out in the real robot.yaml, so no new ROS publishing is implied. **One real bug found and fixed in `scripts/flatten_urdf.py`'s `dae_to_obj`** while converting `top_mount_link`'s mesh (`top_assy_rev1.dae`, 535k triangles, a hand/CAD Collada export like the D435i's — see `dae_to_obj`'s own docstring): it remapped *every* index in a `<triangles>` element's interleaved `<p>` list through the position-vertex `remap` table before slicing out just the VERTEX-offset ones, so a NORMAL index numerically larger than the vertex count threw `IndexError` — `d435.dae` happened to index normals 1:1 with positions, masking this. Fixed by slicing to the VERTEX input's own `offset` *before* remapping. Since `top_mount_link` now has real collision (unlike the old fake alias), `merge_visual_only_links`' cascading merge for the IMU sensor chain (`imu_1_link`/`imu_1_base_link`, both visual-only) now stops at `top_mount_link` instead of continuing all the way to `chassis_link` — confirmed in the actual flattened URDF (no `imu_1` string survives; `top_shelf_link`'s own joint parent is `top_mount_link` directly), so `MODEL_PARAMS["j100_0921"]["imu_link"]` changed from `"chassis_link"` to `"top_mount_link"` accordingly (re-verified live afterward: real, gravity-consistent `linear_acceleration.z ≈ 9.8`, not zero/garbage). `chassis_link` itself is unaffected (still `base_link` — re-confirmed by a successful drive test with no "Articulation controller failed" error, the same live check this project always uses rather than assuming). `camera_optical_link`/`gps_links`/`has_arm` are unaffected too, since they come from `clearpath_sensors_description`'s own sensor macros, unrelated to `mtu32_description`. `robot_data/` and `sim/colcon_ws/` are both `.gitignore`d (large, private lab material, same reasoning as the existing `colcon_ws/build|install|log` entries). **Known follow-up, not chased in this pass**: `top_assy_rev1.obj`'s 535k triangles barely reduce under the existing `DECIMATE_CELL` (0.001 m) — a much heavier asset than anything else in this project's models — worth a dedicated fps check and possibly a coarser decimation cell for this specific mesh if it turns out to cost meaningfully more than the D435i's own (already-tuned) 17k-triangle budget.

**Two more real robots (`a200_0333`, `a300_00036`), same pipeline, no private-package dependency:** unlike `j100_0921`, neither references any private package (`a200_0333`'s `platform.extras.urdf` is an empty `{}`; `a300_00036` has no `extras` key at all), so `generate_description` succeeded first try with no workaround needed. `a200_0333` carries a real D435 camera (not D435i — mounted via `sensors.camera` + a `mounts.fath_pivot` adapter, a Clearpath mount type not seen elsewhere here, but still produces the same `camera_0_link` name `add_camera`'s existing default hand-built-optical-frame path already expects, so no `camera_optical_link` override needed) plus a Hokuyo UST 2D lidar and a Velodyne VLP16 3D lidar (both simulated — see "2D lidar, unblocked" and "3D lidar" below). `a300_00036` carries only a real Phidgets Spatial IMU and **no camera at all** — the first model with none, which needed a new `has_camera` `MODEL_PARAMS` flag (default `True`) to guard `add_camera`/`build_ros_graph`'s camera wiring in `main()`'s spawn loop, since `find_prim` would otherwise raise looking for a nonexistent `camera_0_link`. Two real upstream bugs found and fixed in `scripts/flatten_urdf.py` converting `a200_0333`'s Velodyne meshes (`velodyne_description`'s own shipped `.dae` files, unrelated to this project): (1) they use the literal unescaped string `<STL_BINARY>` as a Collada node id/name, invalid XML, fixed with a narrow text substitution before parsing; (2) once parseable, `dae_to_obj` only ever handled `<triangles>`, but these STL-derived meshes use `<polylist>` instead (confirmed all-triangle via `<vcount>`) — fixed by extending the face-extraction loop to handle both, fan-triangulating `<polylist>` correctly for the general n-gon case too. **`a300_00036` needed the same `chassis_link` fix as a200/j100's own precedents**: the real robot.yaml's Phidgets IMU (parent: `base_link`, visual-only) merges into `base_link`, giving it real visual content it didn't have in the generic a300 model — enough to flip the importer's articulation root there too (hit "Articulation controller failed" at runtime with generic a300's own `chassis_link="chassis_link"`, no import-time warning); fixed with `chassis_link="base_link"`, re-verified via a clean drive test.

**`a300_00036`, updated robot.yaml (supersedes the "Phidgets IMU only, no camera" description above):** the real `robot_data/a300_00036/robot.yaml` grew from 743 bytes to a full field-robot config — D435 (via `mounts.fath_pivot` on `top_plate_mount_c1`, so `camera_0_link` and the default hand-built optical frame, like `a200_0333`), Hokuyo UST 2D lidar (`lidar2d_0_laser`, on `wireless_charger_link`), dual SwiftNav Duro GPS (`gps_0_link`/`gps_1_link` — a300 numbers GPS from 0, unlike the Jackals' 1/2), Microstrain IMU (`imu_0`), Kinova Gen3 Lite arm + 2F Lite gripper on `top_plate_mount_e9`, a wireless charger, and `platform.extras` → `mtu32_description`'s generic `robot_description.urdf.xacro`. `MODEL_PARAMS["a300_00036"]` now has `has_arm`, `lidar2d_link`, `gps_links`, `imu_link="top_plate_link"` (the Microstrain and its empty mount frames merge into the nearest link with real collision — confirmed: `top_plate_link` gains one extra `box` visual) and `chassis_link="chassis_link"` (was `base_link`). **Real bug found and fixed in `scripts/flatten_urdf.py`** (`weld_empty_root_children`, runs after `merge_visual_only_links`, only a300_00036 triggers it today): `base_link` is now a pure frame (no visual/collision/inertial) whose direct fixed children are `chassis_link` (the only one with `<inertial>`) plus arch/estop/button/eth/both GPS/wireless-charger, all of which have `<collision>` so `merge_visual_only_links` leaves them. Isaac's importer doesn't make an empty root a body, so each became its *own* articulation root fixed to the robot's root prim (a non-body, i.e. the world: `physics:body0 = </a300_00036>`, 9 `ArticulationRootAPI`s in `physics.usda` instead of 1) — they'd stay behind when the robot drove, and the drive graph failed with "`.../base_link` is not a valid rigid body or articulation root". Fix: re-parent those 7 joints onto `chassis_link`, origin = chassis_joint⁻¹·joint (chassis_joint is identity here; GPS poses verified against the yaml). Generic a300 never hit this because its extra children are visual-only and merge away. Verified live after a sim restart: 1 articulation root, `drive_test.py` clean (1.02 m at 0.40 m/s), lidar hits (two side/rear wedges at 0.10–0.30 m = the robot's own body; identical after driving, so the mount moves with the chassis), `imu_0`/`gps_0`/`gps_1`/camera/six arm joints publish, an `arm_0_joint_1` command reaches 0.5 rad. **`cut_stem` verified on this robot** (`sim_robot_upstart.launch.py` comes up with all nodes; a full run from the web UI's Cut stem button ends "Cut 20/20 patches", SUCCEEDED, 0 failures/skips, each patch reach → gripper close → pruner confirmed → `drop`, then stow). It first failed every patch with "Gripper action server not available" because `stow_arm_cpp/src/grid_cutter_action_server.cpp` hardcoded `/j100_0921/manipulators/arm_0_gripper_controller/gripper_cmd` (and `servo_twist_topic` `/j100_0921/manipulator/delta_twist_cmds`), and `config/grid_cutter_params.yaml` `pruner_action: /j100_0921/pruner_action_server` — all now **relative** so they resolve under the node's namespace (identical behaviour on `j100_0921`, works on any robot). After editing that package: `scripts/colcon_build.sh --packages-select stow_arm_cpp`, then restart the launch (the running node keeps the old binary). Also fixed: `scripts/colcon_build.sh` only matched 4-digit container names (`^[a-z0-9]+_[0-9]{4}$`), so it silently skipped `a300_00036` ("no running robot containers"); now `{4,}`. Gotcha met on the way: `scripts/fleet.sh` does *not* restart an already-running sim container, so after `gen_urdf.sh` use `docker restart a300-isaac-sim` (the import stamp then picks up the new URDF). One segfault (exit 139, right after the timeline started, no error before it) happened on the first start with this URDF and did not repeat on the next start.

**`a200_0284` (added later; an A200 with the MTU field loadout) — three findings:** (1) it did not "spawn correctly" for two separate reasons. `sim/scripts/setup_scene.py` died with `KeyError: 'a200_0284'` because `MODEL_ASSETS` was a hardcoded tuple of names — it is now derived from every `sim/assets/<m>/<m>.urdf` (the old names kept as a floor), so a new `robot_data/<id>/` robot needs only a `MODEL_PARAMS` entry. (2) Once it spawned, the robot container could not see a single sim topic: its own `robot.yaml` says `domain_id: 1`, `entrypoint.sh` used the real yaml unmodified, and the sim/`.env` are on domain 0 (all the other real robots happen to use 0, which is why this never showed). `entrypoint.sh` now rewrites the copied yaml's uncommented `domain_id` to the fleet's `ROS_DOMAIN_ID` and logs `[entrypoint] <id>: robot.yaml domain_id 1 -> 0` when it differs — the domain belongs to the simulated network, not to a robot's real-world config (`middleware.implementation` is now rewritten to `FLEET_RMW` the same way, logged as `... middleware <real> -> <fleet>`: the `robot_data` copies say `rmw_fastrtps_cpp` while the real robots and the fleet use zenoh). Editing `entrypoint.sh` needs `docker compose build robot0` and a container recreate (`scripts/fleet.sh N`), it is baked into the image. (3) `MODEL_PARAMS["a200_0284"]`: `chassis_link="base_link"` (like a200: real visual/collision and several children; confirmed by a clean drive test, 1.28 m at 0.42 m/s), `wheel_radius=0.157*mean(1.01,0.96)=0.1546` from the real `platform_velocity_controller` override (the left/right asymmetry can't be represented; note the sim robot therefore moves ~6% faster than commanded, since the physical wheel is the URDF's 0.1651 — same "real calibrated value" approach as `j100_0921`), separation multiplier 1.875, max 1.0/1.0, `imu_link="base_link"` (the Microstrain folds into base_link: one extra `box` visual), `imu_index=0`, `gps_0/gps_1`, `lidar2d_0_laser` (SICK LMS1xx; hits in a scan are the robot's own body at ~0.25 m), and a Kinova Gen3 **7-DOF** arm with no gripper (`has_arm`; the arm graph and `configure_arm_drives` match by name/articulation, so 7 joints needed nothing; verified `arm_0_joint_1`/`_4` follow commands). One unexplained Kit startup hang (no `[fleet]` line for 6 minutes, log silent after 35 s) happened on the first start with this model and did not repeat after a second `docker restart a300-isaac-sim`.

**`j100_0922`, `j100_0921`'s twin minus the arm — one real bug, one real physics finding:** identical to `j100_0921`'s own real robot.yaml except its whole `manipulators:` section is commented out (no arm/gripper). `mtu32_description`'s own xacro unconditionally mounts a second camera (`camera_1`, a RealSense D405) on `arm_0_end_effector_link`, assuming every Jackal running it has the Kinova arm — with none configured here, that link is never defined, leaving `camera_1`'s mount joint (and, once that's removed, its own now-orphaned child joint) referencing links that don't exist anywhere in the URDF. `scripts/flatten_urdf.py` gained a general (not `j100_0922`-specific) `prune_dangling_joints` pass, run before `merge_visual_only_links`, that drops any joint whose `<parent>` was never actually defined as a link, cascading to catch newly-orphaned joints too. `chassis_link`/`imu_link`/etc. are otherwise identical to `j100_0921`'s (re-verified live, not assumed). **Physics finding, now fixed (mass):** `j100_0922` tipped over (pitched to ~77° and stayed there) within a few seconds of driving, in either direction and even at 0.2 m/s, about every other attempt. Cause, read from PhysX with `Articulation.get_link_masses()`: the sim weighed **75 kg** (URDF: 18.4 kg) because every URDF link without `<inertial>` becomes a rigid body whose mass PhysX computes from its collider at 1000 kg/m³ (`top_mount_link`, a 267k-vertex mesh, 29.8 kg; each 11 cm GPS sphere 5.9 kg) and a collider-less frame link defaults to 1 kg (13 of them), all of it high above a 26 cm wheelbase. `fix_massless_bodies` (opt-in per model: `MODEL_PARAMS["j100_0922"]["massless_density"]=100`, `frame_mass=0.02`) gives those bodies density 100 kg/m³ / 0.02 kg at spawn (total 26.5 kg); it must run before the timeline plays, PhysX ignores a runtime mass change in its tensor view. After it: 0 flips in 4 reverse trials at -0.6 m/s plus a full sweep (before, about every other trial flipped), and the robot passes the calibration sweep. **Not applied to `j100_0921` (the same top frame and GPS spheres, ~95 kg instead of ~34 kg) nor to `a200_0284`/`a300_00036`, because their `cut_stem` runs were tuned with the current masses; it stays stable, but check `get_link_masses()` before trusting its dynamics.**

**Middleware on the physical robots (2026-10-07):** a300_00036 and a200_0284 run zenoh (`rmw_zenoh_cpp`, zenoh 1.8.0); the others weren't checked. Details and how-to in `scripts/CLAUDE.md` ("Real robot middleware"). For a robot that a base station or RViz talks to over WiFi: (1) remote sessions must be zenoh *clients* (`mode="client"`) of the robot's router or of the base station's router -- in peer mode (the default) topics show up but no data arrives; (2) give it `scripts/zenoh_router_config.py`'s router config through robot.yaml `system.ros2.middleware.profile` (WiFi egress rate limits; check the WiFi interface name, `ip -br addr`, and that the limited topics exist under that robot); (3) expect a 0.3 s pause of its data per new remote subscription and seconds for RViz-sized subscribe/unsubscribe bursts (robot router CPU), not fixable in config. a300_00036: router config in place (`~/zenoh_config/router.json5`, WiFi `wlp3s0`); `~/cyclonedds_config/` is left from a Cyclone DDS trial and unused. The others: not set up (a200_0284 had Clearpath's default router config on 2026-10-06; the rest unchecked).
